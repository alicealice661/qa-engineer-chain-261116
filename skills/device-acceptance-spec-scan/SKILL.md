# 设备验收规范 · 生成与扫描

## 链路位置（本包 qa-engineer-chain，先看这段再动手）

- **上一棒**：`device-auto-test-plan-authoring` 的阶段划分，或用户已有的需求/测试过程档案。
- **本技能**：先把「应然」（验收规范：功能域 + UI 验收卡 + 清单 + 豁免）与「实然」（扫描结论）**分文件**产出。
- **下一棒**：扫出的问题 → `zentao-bug-autosubmit` 提单；若问题指向接口层 → `apk-network-pentest-recon` 做接口还原。
- **别用本技能做**：① 要设计测试用例（用例表/Excel）→ 用测试用例类技能，不是本技能；② 要自动驱动流程 → `device-e2e-flow-driver`；③ 只要一份「这设备有什么功能」的介绍 → 直接读界面，不必出规范。
- **红线**：规范里不许写「大概跑通」这类不可判定项；每条要么可客观核对，要么进 K 系列豁免并写明理由。
把「**规范（应然）** → **AI 扫描（执行）** → **报告（问题/根因/解法/回归）**」固化为一条可复用流水线。

## 一、第一原则：应然与实然必须分文件

这是整套方法成立的前提，也是**最常犯的错**：

| 文档 | 性质 | AI 是否读 |
|---|---|---|
| **验收规范** | **应然**：功能规格 + UI 验收规格 + 判定规则 | ✅ 唯一判定依据 |
| **检查清单 JSON** | 规范的机器可读展开 | ✅ 遍历入口 |
| **扫描任务书** | 执行步骤 + 禁止项 + 输出格式 | ✅ |
| **测试过程档案**（旧报告/台账/变更流水） | **实然**：我们做过什么、发现过什么 | ⛔ **不必读** |

> **把"要求"和"曾经发现"混在一个文件里，AI 就分不清该判什么 → 判定必然失真。**
> 历史发现中**会影响判定**的部分，提炼成「已知正常语义」豁免清单；其余一律留在档案里。

## 二、交付物四件套

```
规范/
  ├─ <设备>_设备验收规范_v1.0.md      ← 主规范（唯一判定依据）
  └─ AI扫描任务书.md                   ← 可直接复制的 prompt + 执行细节
conf/
  └─ acceptance_checklist.json         ← 机器可读检查项（每条带 method/params/severity/exempt/verdict）
templates/
  └─ 输出模板_问题卡与回归报告.md
reports/
  ├─ 规范扫描报告_<日期>.md
  └─ scan_result_<日期>.json           ← 逐条判定（由 checklist + verdicts 合并生成）
```

**主规范骨架**（照填即可，并为其他设备复用）：

```
§0 铁律 R1–R12（版本快照优先 / 不臆测 / 禁硬编码坐标 / 禁拍脑袋阈值 /
                触发面须核实 / 只读优先 / 双源采集 / exec-out 计数 /
                adb 串行 / 已知语义不判FAIL / 归因先取证 / 进程归属必查）
§1 设备身份基线      —— 一表：型号/系统/分辨率/包名/版本/接入 + 每项校验命令 + 不符时的中止规则
§2 功能规格          —— 功能域清单 → 每域一表：ID|功能|入口|预期行为(可观测契约)|判定源|类型
§3 UI 页面验收规范   —— 通用标准 U1–U8 + 逐页验收卡（元素|期望|定位方式|判据）+ 跨页一致性 C-x + 定位规约
§4 判定规则          —— 三态判定 + 判定参数表(唯一阈值来源) + 已知正常语义 + 证据四层 + 采集规约
§5 客观不可判定项     —— 诚实声明缺口，防 AI 硬判
§6 输出规约          —— 问题卡 / 扫描报告 / 回归报告 三段模板 + C/D 编号规则
§7 扫描执行 SOP      —— Step0 前置校验 → Step1 建基线 → Step2 功能面 → Step3 UI 面 → Step4 判定取证 → Step5 输出
附录A 生成范式        —— 本骨架的复制说明
附录B 已知异常登记    —— 回归时必须复核的清单 + 给研发的改进建议
```

## 三、生成规范的 4 步法

1. **静态打底**：`adb pull` APK → 解析 manifest（组件/权限/导出属性）+ DEX（类与调用点）→ 得**组件面与权限面**。
2. **实机坐实**：逐个入口用**真实点击链**走通。
   ⚠️ **禁用 `am start` 代替入口验证**——它只证明"能渲染"，**不证明"用户可达"**。
3. **标定参数**：对每个判据**实测取阈值**（进度条几何、颜色签名、模板 NCC 明暗两态…）→ 填 §4 参数表。
4. **沉淀豁免**：把测试中所有"曾误判"的现象逐条写成 §4「已知正常语义」K 条款。
   > 这一节是规范里**最有复用价值**的部分——它把踩过的坑变成豁免条款。

## 四、扫描 SOP（AI 侧）

```bash
D=<ip>:5555
adb connect $D

# Step0 前置校验（阻断项！）
adb -s $D shell dumpsys package <pkg> | grep -aE 'versionName|versionCode|lastUpdateTime'
adb -s $D shell wm size; adb -s $D shell getprop ro.build.version.release
adb -s $D shell ps -A | grep -aE '<pkg>|<engine_pkg>'
#   → 与规范 §1 基线不符：立即中止，只报告"基线不符"，不判任何功能/UI 缺陷

# Step1 建采集基线
adb -s $D exec-out logcat -d | wc -l          # 记录起始行数（环形缓冲小，必记）
adb -s $D exec-out ls -la /sdcard/<snapdir>/  # 计数一律 exec-out
adb -s $D shell run-as <pkg> cat /data/data/<pkg>/shared_prefs/<pkg>.xml   # 明文配置

# Step2/3 逐条执行 conf/acceptance_checklist.json
# Step4 每条给 PASS/FAIL/UNKNOWN/SKIP + 证据（FAIL 必挂 L1 或 L2）
# Step5 出报告 + scan_result.json
```

**判定三态纪律**：`UNKNOWN`（客观不可判定）必须写明"为什么 + 需要什么"，**不得降级为 PASS 蒙混，也不得升格为 FAIL 硬判**。

## 五、抗静默失败设计（**本方法最容易翻车的地方**）

解析/取证脚本一旦把异常 `except` 吞掉，就会**静默输出"未找到"**，然后你据此得出错误结论。**本项目已因此白跑两轮。**

必做三条：
1. **统计并打印扫描量**（扫了多少类/方法/帧）+ **异常计数**；
2. **设置阳性对照**——已知必然命中的样本；对照为 0 就**报错退出**，而不是报告"未找到"；
3. **遍历前先用一个样本验证 API 可用**（拿一个方法确认能取到字节码），再全量跑。

## 六、高频陷阱（逐条都是实测踩出来的）

| 陷阱 | 正确做法 |
|---|---|
| 用 UI 特征判版本 | **只认 `versionName`**（背景插画会轮播，同版本外观会变） |
| 点击坐标硬编码 | 自绘页用 `cv2.matchTemplate` **动态求坐标**；原生页用 `resource-id` |
| 阈值凭经验设 | **必须实测标定**：曾把进度条 `min_line_height` 设 250，而第 1 步实际只有 175 → **整段被滤掉**；模板 NCC 设 0.8 会漏检按钮暗态（实测暗态仅 0.61）→ 取 0.6 |
| `adb shell ls \| wc -l` 计数 | **失真可达 4 倍**（PTY 换行转换）→ 一律 `adb exec-out` |
| `grep -m1 mCurrentFocus` | 首行恒为 `null` → 页面变化永远检测不到；用 `grep -a mCurrentFocus \| tail -1` 或查 `ResumedActivity` |
| 并发发 adb 命令 | **必串行**（互踩产生假失败） |
| 看到崩溃就判缺陷 | **先看 `Process:` 字段**确认进程归属（独立进程崩 ≠ 被测进程崩） |
| 解析列表用多字段 `zip` 或"左边界 x 相等"分组 | `zip` 会**静默截断**（制造假通过）、左边界分组会**把一张卡切成两条**（制造假失败）→ 按 **x 区间聚类** |
| 只看落盘终态判"是否写入" | 缓存目录常是"**存新删旧**"→ 会把"保存后被覆盖"误判成"从未保存"。须**写入日志 + 删除日志 + 磁盘终态 + 跨会话复核**四线并看 |
| 归因为"采样率不足""工具漏采" | **先逐帧扫描坐实**，再归因。误归因会让整改方向错一整轮 |
| `cv2` 读非 ASCII 路径 | 用 `np.fromfile + imdecode` / `imencode(...).tofile()` |
| `androguard`：`APK.get_all_dex()` | 返回**原始 bytes**（不可解析）→ 遍历类要用 `AnalyzeAPK` 返回的 **DEX 对象列表** |
| `androguard` 类名匹配 | 形如 `Lcom/x/Y;` → 尾匹配用 `'/Y;'`，**不是** `'.Y'` |
| `androguard`：`get_fields()` | **不含继承字段** → 须查父类链 |
| 软键盘遮挡底部按钮 | 点底部按钮前先 `keyevent 4` 收键盘；`keyevent 66`(ENTER) 不一定触发提交 |
| 托管 Python 无 cv2 | 用带 cv2 的 venv（如 `~/.workbuddy/binaries/python/envs/default/Scripts/python.exe`） |

## 七、输出纪律

- **问题卡**：现象 / 根因 / 解法 / **触发方式（必填）** / 违反条款 / 证据 / 状态。**仅 adb·外部注入可触发的必须标注"正常使用不受影响"**。
- **根因写到机制层**：堆栈是现象不是根因。格式：`{证据源} 显示 {原文} → 因此 {机制} → 导致 {现象}`。
- **C/D 双轨 + 4 步确认**：`C-xx`（候选）→ ① 稳定复现 ② 违反契约 ③ 跨证据一致 ④ 非环境抖动 → 全过才升 `D-xx`。
- **验收期望必须写落点**：❌"back_iv 可点且能返回" → ✅"点击后返回**主页（SplashActivity）**"。
  > 实测教训：只写"能返回"的条款，让一个"**能返回、但返回错了页**"的 P2 缺陷溜过了判定。
- **扫描也回修基准**：扫描发现判定口径有问题时，同步改规范（并在变更记录里写明），否则下一轮还会漏判。
