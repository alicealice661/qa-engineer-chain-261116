# 设备端自动化测试计划编制

## 链路位置（本包 qa-engineer-chain，先看这段再动手）

- **上一棒**：用户给设备型号 + 业务场景（如「仿照晨检仪的流程，给出入库秤做个计划」）。
- **本技能**：产出一份**研究计划 md**（分层策略、用例 A~F/W 分组、分阶段执行、授权边界、前置待确认）。
- **下一棒**：`device-acceptance-spec-scan` 把计划落成可扫描的验收基准；若要走接口路线，则转 `apk-network-pentest-recon`。
- **别用本技能做**：① 要「验收规范 + 扫描结论」→ `device-acceptance-spec-scan`；② 要直接跑通多步流程 → `device-e2e-flow-driver`；③ 要具体接口用例代码 → `device-api-layer-autotest-scaffold`。
- **本技能只出计划，不出用例表、不跑设备。** 用户说「下一步怎么实现自动化」时，先给计划，不要跳到写代码。
在**动手写代码之前**，为新设备产出一份可评审、可执行的自动化测试研究计划。这是"规划"阶段的能力，与执行阶段的 skill（`device-e2e-flow-driver` 跑流程、`android-adb-test-monitor` 做监测、`device-acceptance-spec-scan` 做验收扫描）互补。

> **落地衔接**：计划批准、进入「阶段 3 工程骨架」时，改用 **`device-api-layer-autotest-scaffold`**（含接口层骨架结构 + 5 个必踩坑：签名输入必须与发送体逐字段对齐 / 验签失败当 oracle 反查 DTO / 未导出 Activity 不能 am start 只能点入口 / 无 root 设备动画页 dump 降级截图 / fixture 作用域）。

## 二、第一决策：分层下沉

规范 §3 铁律：**能下沉到接口层验证的，不放到界面层**。

落地动作：先画一张"三层覆盖边界"图（接口层 / 界面层 / 硬卡点），再决定每条用例写在哪层。
- 签名/加密可复现的设备 → **接口层为主力**（可全自动、可脱离设备，是最大杠杆）
- 只有 UI 能证明的（渲染、联动、跨页一致性、设备本地状态）→ 界面层

## 三、第二决策：硬卡点识别与路线

| 卡点 | 表现 | 三条路 |
|---|---|---|
| 人脸/生物识别 | 自绘层 `uiautomator dump` 空壳，流程进不去 | **A 接口层绕过**（推荐）/ B 现场人工配合 + 脚本接管 / C frida gadget 重打包（不建议，改变被测对象） |
| 写入类操作 | 改库存 / 考勤 / 配置，不可逆 | 默认只读；`e2e_write` mark 物理隔离；需授权 + 回滚方案 |
| 无 root | 不能抓包 / 注入 / 改系统证书 | 证据改走应用自身日志（如 okhttp 全量日志）；**不假装有抓包能力** |

## 四、E2E 的位置（最易漏的一环）

**E2E 不是某一层的用例，是"单点都通之后"的串联层**，必须**单列为一个阶段**，且排在最后。

依赖前置：签名通 → 框架通 → 单点用例通 → 硬卡点路线定。
E2E 是写操作 → 默认只写用例不执行，等授权。

> 实测教训：初版计划把 E2E 隐含在"界面层"里没单列，被追问"端到端属于哪个阶段"才发现缺口。

## 五、用例分组惯例（沿用全部门命名）

| 组 | 内容 | marker |
|---|---|---|
| A | 设备可用性基线 | smoke |
| B | 首页 / 列表数据一致性 | consistency |
| C | 详情页 / 二级页 | consistency |
| D | 设置页 | readonly |
| E | 增强校验（视觉 / AI） | vision |
| W | 网络通道 / 接口层 | readonly |
| F | 写入类流程（**不执行**） | writeflow / e2e_write |

每组用 `编号 | 用例 | 断言要点` 三列表，组头标注条数与 marker。

## 六、设备差异适配

| 设备特征 | 适配动作 |
|---|---|
| UI 有 `resource-id` | 界面层走标准定位链（规范 §5.1），成本低 |
| UI 自绘（dump 空壳） | 降级模板匹配（OpenCV `matchTemplate`），坐标动态求，**禁硬编码**；断言优先走数据库 / 日志 / 接口 |
| 无 root | 见 §三 |
| 有签名 / 加密 | 反编译还原算法 → 接口层可自动化（**最高价值项**，值得单列阶段 0 阻断项） |

## 七、必写的三块（缺一不可）

1. **约束条件表 C1-Cn** —— 至少含：只读优先、计数用 `adb exec-out`、adb 必须串行、定位降级链、写操作标记隔离、后端可达前提
2. **授权边界表** —— 只读 ✅ 允许 / 界面导航点击 ✅ 允许 / 写入类 ⚠️ 需授权 / 批量清零与删除 ⛔ 不做
3. **前置待确认清单** —— 明确列出"需要你先给什么"（后端是否可直连、硬卡点走哪条路、写入是否授权、有无测试账号），**不给就不开工，禁编造**

## 八、纪律

- 所有阈值**实测标定**，禁经验值
- 视觉基线**禁整页比对动态数据页**（规范 §6.1），只对静态骨架判失败
- 问题格式三栏：现象 / 根因 / 解法（+ 触发方式 + 证据 + 状态）
- C/D 双轨 + 4 步确认
- 分阶段执行里标注**「你主导，我配合」/「我执行」**，让责任边界清晰
- 输出路径：`Desktop\自动化测试\<设备>设备端自动化测试\规范\<设备>_AI自动化测试研究计划.md`
