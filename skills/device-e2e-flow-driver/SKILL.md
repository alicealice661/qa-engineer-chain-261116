# 设备多步流程自动化驱动

## 链路位置（本包 qa-engineer-chain，先看这段再动手）

- **上一棒**：`device-api-layer-autotest-scaffold` 已把「软件可自动」的部分下沉；`selfdrawn-ui-template-locate` 提供自绘页的点击手段。
- **本技能**：把多步业务流程做成**可重复的自动化驱动**（能力边界 → 判步指纹 → 逐步点击不达标拒点 → 双源断言）。
- **下一棒**：跑出的现象与证据 → `android-adb-test-monitor` 做取证/复测报告；缺陷 → `zentao-bug-autosubmit` 提单。
- **别用本技能做**：① 单个接口的验证 → `device-api-layer-autotest-scaffold`；② 只想要一份「这流程能不能自动化」的判断 → 本技能第 0 步单独就够，不必写驱动；③ 只抓日志出报告 → `android-adb-test-monitor`。
- **红线**：物理环节（刷脸、真实称重、机械动作）不许用「注入成功」冒充「验收通过」，两者要分开记录。

## 何时用
- 用户问「**能不能全流程自动化**」「跑一遍完整流程」
- 已能定位单个控件，但要把它们**编排成一条流程**跑通并出结论
- 需要判断「哪些步骤真的能自动、哪些不能」并给出**量化的人工残留**

## 第 0 步（最容易跳过、也最值钱）· 先划能力边界

**不要上来就写脚本。先去界面把每一步的交互方式看清楚。**

做法：翻历史录屏抽帧 / 现场走一遍，对每一步回答一个问题 —— **这一步靠什么推进？**

| 推进方式 | 可否自动 | 例 |
|---|---|---|
| 软件发出的事件（触屏点选、按键） | ✅ 可自动 | 健康问答点选项、点「完成晨检」 |
| **物理世界的输入**（人脸入镜、手伸进相机、称重、扫码） | ❌ **物理约束** | 人脸检测、手部检测 |
| 人工判断（听声音、看灯） | ❌ 需人耳/人眼 | 语音是否真出声 |

**产出**：一张「能力矩阵」表（步骤 × 交互方式 × 可否自动）。这张表就是交付物的一部分，**比脚本本身更重要** —— 它决定了用户对"全自动"的预期。

> ⚠️ **"物理约束"这四个字别急着写死**：生物识别类（人脸/手部）的"物理输入"**可能被静态替身解除**（实测一张手机屏幕照片即通过人脸检测并推进到下一步）。判定顺序：**先按本节做一次探活体实验，再决定该步标"可自动"还是"物理约束"**——详见下文「生物识别环节」一节。结果是"能过"时，这句话同时是**工程好消息**（可无人值守）和**验收坏消息**（安全缺陷），两面都要写进交付。

> 经验：真实设备里，**"全自动"往往等于"人工从 38 秒降到 10 秒"**，而不是零人工。把这句话明说，避免过度承诺。

## 第 1 步 · 找一个"稳定的几何量"当判步指纹

不要用 OCR 判"现在在哪一步"（慢、脆）。找流程里**结构性不变**的量：

```python
# 例：右侧常驻进度条，绿线高度与当前步成线性关系
step = round((line_bottom - line_bottom_offset - step_y0) / step_dy)
```
- 五步流程 → 得到一个 0~3 的整数状态，**比任何文案判断都稳**
- 关键参数（`step_y0` / `step_dy` / `line_bottom_offset` / 色域）**收敛到一份配置**，别散在代码里
- **必须加"非流程帧过滤"**：主页也有同色元素。用 `min_line_height` 滤掉，但**下限别设太高** —— 实测第1步的绿线只有 175px，滤网设 250 会把整个第1步误判成"非流程帧"（这个坑很隐蔽：表现为"某一阶段样本突然消失"）
- 离线回归：拿历史帧跑一遍判步函数，**期望值写死对照**，改参数就跑回归

## 第 2 步 · 按步定位点击（不达标一律拒点）

```
循环：截图 → 判步 → 若 == 目标步 → 定位控件 → NCC ≥ 阈值才 tap
```
**三条纪律**：
1. **脚本内零硬编码坐标**，坐标只能来自匹配峰值
2. **定位不达标 → 拒绝点击**（"最相近也点一下"是灾难）
3. **每步动作前的截图要存档** —— 失败时它就是唯一的现场

**第四条纪律 · 点击闭环（`tap` 必须配"校验 + 重试"）**：`tap` 之后**必须校验预期变化**（Activity 切换 / 判步推进），未生效则**重试**。因为控件可能正处在**淡入/未就绪窗口** —— 此时形状已命中，但点击被应用吞掉。

```
for att in range(5):
    img, r = wait_el(name, timeout=40, mature=True)   # 形状命中 + 颜色成熟
    tap(img, name)
    if wait_activity('FeatureActivity', 6): break     # ← 点后校验
    sleep(2.5)                                        # ← 未生效则重试
```

**成熟判据怎么定（别拍脑袋）**：对同一控件连拍淡入全过程，取一个**分离明显**的物理量。实测半透明蓝按钮（启动后逐帧，工具 `home_fade_probe.py`）：

| 状态 | NCC | 平均饱和度 S |
|---|---|---|
| 白态（未绘制） | 0.57 | 72 |
| 淡态（淡入中） | 0.52 | 119 |
| **成熟态（可点）** | **≥0.78** | **152~158** |

→ 阈值取 `S≥140`。但记住：**成熟判据只是"加速"**（少点无效），**点击闭环才是兜底**（不依赖任何阈值猜测）。

## 第 3 步 · 双源断言（缺一不判 PASS）

界面证据 + 数据证据**必须同时成立**：

| 源 | 取法 | 例 |
|---|---|---|
| 界面 | 截图序列 / 关键节点帧 | 进度条推进、提示条出现 |
| 数据 | `logcat` 事件 / 落盘文件 / 后端记录 | `上传成功`、`insertCheckRecord` |

> 有的步骤**界面无独立态**（例：第5步"完成"不体现在进度条上），此时**只能靠日志**判 —— 所以断言设计要**按步骤分别定义判据**，不要一套吃到尾。

## 第 4 步 · 证据目录结构

```
evidence_rN/run_<分支>/
  frames/      p00_home_before.png … p07_home_tip.png   # 按阶段命名，★失败帧也存
  logcat.txt                                            # 全程
  result.json                                           # checks + 完整日志文本
```

## 一次启动跑多分支对照（串联复跑）

要验证"同一套交互在**不同分支**下都成立"（如正常上岗 vs 离岗休息），**别开两次任务** —— 把分支串成一条命令：

```bash
PY e2e_driver.py run --live --state normal 2>&1 ; \
echo "=== 趟B ===" ; \
PY e2e_driver.py run --live --state leave --symptoms 1 2>&1
```

- 用 `;` 而非 `&&`：**前一分支超时不得阻断后一分支**（现场只有一次机会，别浪费人的站位时间）
- 每趟 `--out` 留空 → 各自按时间戳建目录，**天然分离**，不用手动命名
- **必须提前告知物理环节节奏**：趟与趟之间用户要**再做一次人脸/手部**，脚本会在第 1/2 步等待 —— 不说清楚，用户会以为跑完了就走人
- 收尾产出**双分支对照表**（同维度逐行比），一眼区分"全流程共有的成立"与"分支特有的行为"

对照表维度建议：进入流程耗时 / 物理步骤耗时 / **分支特有交互**（症状展开与否）/ 提交→返回耗时 / 各断言 / 被测进程崩溃数。

> 实测：两分支串联各跑一趟（正常上岗 78s、离岗休息 82s），均 **1 次点击生效、零重试**；对照表直接暴露"正常上岗**不展开症状**（符合 P-02-9）vs 离岗休息**症状必填 11 项**（符合 P-02-10）"这一分支差异。

## 答题类步骤：**试错作答**（别赌"第一项就是正解"）

带判分的问答步骤（健康问答 / 知识考核 / 确认题）**不要盲选第一个选项** —— 正解可能在任何位置（实测三题正解分别落在 B、C、D，第一项 A **三题全错**）。

**做法：答错判据 + 穷举**

1. **先量出"答错"的可观测签名**（比找"答对"容易得多）：实测提示条是一块固定 ROI 的红框红字。
   ```python
   # 判据：提示条 ROI 内红色像素占比。实测 无错 = 0.000 / 答错 ≈ 0.05 ⇒ 阈值 0.02，分离度极高
   def is_wrong(img, roi=(46, 840, 1186, 920), thr=0.02):
       return red_ratio(img, roi) > thr
   ```
   **量阈值的方法**：拿"答错帧 / 未答帧 / 答对帧"三种历史帧各算一遍，看分离度；**不要目测红框位置**，用行/列红色像素直方图把 ROI 找出来。
2. **穷举换项**：`A → B → C → D`，每次点击后**等一个固定的渲染+判分周期**（实测 ~2s）再判错，答错就换下一个；题数 × 选项数 = 最大点击次数（3×4=12）封顶。
3. **每题通过后必须确认界面真的推进了**（下一题 / 进入下一步）—— 见坑清单"假通过"。
4. 注意**选项数不固定**（实测有的题只有 3 项，第 4 项为空）→ 定位不到就跳过，别死等。

> 副作用提醒：**答错也会被上报**。实测每点一次=1 条 `答题记录提交`，9 次点击 → 9 条记录（含 6 条错误答案）。跑试错作答会**污染后端答题数据**，跑完需清理，并在报告里注明。

## 用「后端配置」当独立裁判（比界面更硬的第 3 方证据）

界面与日志是"被测系统自己说的话"；**服务端下发的配置是第 3 方**，能一举把"是配置错了还是实现错了"切开。

**取地址**（不用猜、不用逆向）：
```bash
adb shell run-as <包名> cat /data/data/<包名>/shared_prefs/<包名>.xml
# → PROJECT_SERVER / PROJECT_PORT / canteen_id … 关键参数全在 prefs 里
```
**调接口**（从应用日志里找端点名与调用形态）：
```bash
# 应用日志会写明 "Request Succeeded:操作成功, :<模块>/<方法>"；返回体一般不在日志里 → 自己调
curl -X POST "http://<SERVER>:<PORT>/app/<模块>/<方法>" \
     -H "Content-Type: application/json" -d '{"canteenId":30}'
# 若报 "Required request body is missing: ... <VO 类名>" → 说明该端点要 POST + JSON body，报错信息直接给了 VO 类名
```
**用配置做判据**：把配置字段与界面行为逐条对照。**配置稳定（连调 3 次一致）才能排除"每轮随机"**，否则先证伪随机性再下结论。

> ⚠️ **纪律（血的教训）：以"后端配置"为判定依据前，必须先确认该配置近期是否被测试方/运维改动过。**
> 步骤：① 读返回的 `updateTime` / `updateBy`；② 与本次测试的动作时间对齐；③ **开口问一句**"这个配置最近有人改过吗？"
> 实测踩坑：曾把某题的"正确答案"配成与题干语义相反的值，连调 3 次稳定 → 判定为 **P1 产品缺陷候选**并上报。事后确认：**是测试方自己为了构造"答错→换项"场景在后台手改的**，`updateTime` 就在实机前 20~30 秒（信号已捕捉，却仍先行定性）→ 撤回。
> **正确顺序**：先看 `updateTime`/`updateBy` 是否异常靠近测试时间 → **先确认** → 再定性。

> 实测价值（正例）：一次调用把"某步为什么卡住"从"猜"变成"实锤"——后端下发的是**唯一正解**（`solution` 字段，位置随机），于是"答题"步骤必须**试错作答**而不能盲选第一项。**这类机制光看界面只能看到"答题错误"，看不到"为什么"。**

## 生物识别环节：**先用"静态替身"探活体强度**（一举两得）

第 1/2 步若是"人脸的物理输入"，别急着把它划成"不可自动"。**先做一次探活体实验** —— 成本 5 分钟，结果二选一，**两条都有产出**：

| 结果 | 工程意义 | 验收意义 |
|---|---|---|
| 照片**能**过 | **物理约束解除 → 可无人值守回归** | **安全缺陷**（代打卡风险）→ 必须报 |
| 照片**不能**过 | 物理约束真实存在，接受边界 | 防伪有效，登记为"已验证" |

**做法（只推进到目标步，绝不提交，零业务副作用）**：
1. **硬件/软件侦察（离线可做）**：
   ```bash
   # 双目？USB 摄像头型号
   adb shell 'for f in /sys/bus/usb/devices/*/product; do echo -n "$(dirname $f|xargs basename): "; cat $f; done'
   # → 常见形如 0c45:6360 RGB Camera / 0c45:6361 IR Camera（IR 存在 = 有能力做红外活体）
   ```
   再看 APK：`libarcsoft_face_engine.so`、`libyolov8ncnn.so`（图像识别）、以及字符串 `活体检测`/`IR活体`/`请放入双手手心`。
   **"有 IR 硬件 ≠ 已启用 IR 活体"**（不少厂商买了双目只跑 RGB）→ **必须实测**。
2. **量化判据：逐帧相似度**（比"识别成功"这种事件布尔值强得多）
   ```
   RecognizeService: i  Result:0, :<相似度>     # Result:2 = 无脸；≥0.9 触发匹配成功
   FeatureActivity: e  Face recognition succeeded
   getCanteenEmployerInfo uuid:N → custom msg{employeeName}
   ```
   **用真人脸先跑一次拿基线**（实测真人峰值 **0.9092**），再用替身跑 —— **替身分数常比真人还高**（平面、无运动模糊、光照均匀），这本身就是"翻拍"的辅助特征。
3. **判"是否真的推进"用下一环节的启动日志**（最硬），别只信界面判步：
   ```
   初始化手部相机 id=127   +   TTS「请放入双手手心」   ⇒ 已过第 1 步
   ```
4. **设备自证**：识别瞬间应用常会**自己存一张抓拍**（实测 `HandPhotoSaver: 保存照片成功: /sdcard/faceCheck/<ts>.jpg`）——**拉下来看内容**，若画面里是"手机屏幕上的脸"，这就是最硬的一条证据。
   ⚠️ 注意目录命名可能骗人：实测该目录名/类名都像"手部照片"，实际存的是**人脸识别瞬间抓拍**。**别凭名字归类，拉图看。**

**甄别"是否真的匹配到替身"**：界面帧要能看到"举着照片的手 + 引导圈套在照片上"，且**真人脸不在取景框内**。
> 终极对照实验：**让另一个人手持被识别人的照片**（持照人 ≠ 被识别人）—— 物理上排除了"匹配到真人脸"的唯一替代解释。这一步是"候选 → 确认（C→D）"的关键。

## 第三类物理输入：**相机取流（MJPEG，自绘 UI）—— 注入点与 Camera2 完全不同** ★

设备上还有一类"要看画面"的页面，**根本不是本机 Camera**，而是 **MJPEG over HTTP 自绘渲染**。
判据（一眼认出，别上来就找 Camera2）：

| 信号 | 说明 |
|---|---|
| dump 里有 `*mjpg*_view` / `*mjpg*_surface` 之类的 SurfaceView id | 十有八九是 MJPEG |
| 画面上有 `LIVE` 角标 | 实时流，非静态帧 |
| 类名含 `MjpgSurfaceView` / `MjpegInputStream` / `MjpegViewThread` | 已确认 |

**定位手法（5 分钟）**：frida `Java.use("<Xxx>SurfaceView")` 打字段/方法 + `Java.choose` 读实例字段，
**直接把 `streamUrl` 读出来**，不要靠猜路径：

```js
Java.choose("com.x.view.widget.MjpgSurfaceView", {
  onMatch: function (inst) { log("streamUrl=" + inst.streamUrl.value); },
  onComplete: function () {}
});
```

**实测案例（出入库秤·物料学习页，2026-10-15）**：

```
streamUrl = http://127.0.0.1:17339/camera-images?stream=true     ← 流
             同服务不带参数 = 单帧 image/jpeg（640×480，~71KB）
类结构：MjpgSurfaceView ─ $MjpegViewThread.connectToStream(String) → HttpURLConnection
                        └ $MjpegInputStream(InputStream).readMjpegFrame() → Bitmap
                        └ $OnFrameCapturedListener.onFrameCaptured(byte[])   ★ 抓帧出口
         业务侧：XxxActivity.onTakePhotoAndLearn() → runLearnFlow()
                 → lambda$onTakePhotoAndLearn$1(byte[])                    ★ 消费同一份 byte[]
```

**注入点 = 抓帧回调 `onFrameCaptured(byte[])`**（不是相机预览回调）：
- 数据是 **JPEG 原始字节**（magic `ffd8ff`），不是 NV21 —— 素材直接给一张 JPEG 即可，不用做格式转换；
- hook `captureFrame(OnFrameCapturedListener)`，用 `Java.registerClass` 包一层 listener，
  `onFrameCaptured` 里先把真实帧落盘（`/sdcard/Download/xxx.jpg`）**再决定放行还是替换** —— 落盘的真实帧是"取证素材 + 格式样本"。

> ⚠ **服务在 App 自己进程里**（实测：`com.ali.shcema` pid 同时监听 17339，loopback）。
> 所以**不能用 iptables / 中间人 / adb forward 改写流**（PC 侧转发只影响 PC）；**只能 frida hook**。

**这条链路的"两段式"要写进断言**：点一次"拍照/学习"，logcat 里会**先识别、后写入**两段：
```
>>> 拍照学习: name=X, code=Y
>>> 识别结果: {"products":[{sku,name,confidence}...],"hasPrediction":true,"errorCode":0}
MaterialRecognizeUtil: learnItem: success, code=204
```
`confidence` 全低于页面阈值（该设备 `et_min_score=30%`）时"不自动填充物料" —— **阈值是界面字段，不是常量**，别写死。

**写闭环的回滚纪律（踩过的坑）**：这类"学习/训练"型写入，**删除粒度常常是"整个对象全删"**，
不是"删最近一条"（实测弹窗原文：「删除该物料的**全部**学习记录…识别能力将失效」）。
⇒ **动手前先点一次"导出"做备份**，并明确记下"回滚会连带删掉历史数据"——否则一次验证就毁掉基线。
导出常是"两条产物"：`metadata.bin`（映射体）+ 打包 `*.zip`；**比体积**是最省事的落库证据
（实测学一条记录：`129157 B → 131419 B`）。

**还原：系统 picker 用「D-pad 焦点事件」，别用 `input tap`** ★★（本条推翻了早期错误结论）
界面「导入」走系统 `DocumentsUI/.picker.PickActivity`。**文件卡片不响应触摸**：`item_root` 的 `clickable=false`，
`input tap` 打在卡片中心 / 文件名 / 缩略图上**一律无效**（曾据此误判"不能自动化"）。
**真正可行的手法 = 焦点事件**：
```
input keyevent 20   # DPAD_DOWN / 19=UP  移动焦点
uiautomator dump    # 读 focused="true" 节点的 bounds，核对是否落在目标项（比对 title 文本）
input keyevent 23   # DPAD_CENTER 确认 —— 立即生效并返回上一页
```
⇒ 教训：**`clickable=false` ≠ 不可交互**；控件只吃焦点事件时，`input tap` 会静默失效。
排查顺序：先 dump 看 clickable 分布 → 若全 false 就改走 keyevent，别急着下"不可自动化"的结论。
（另：导出目录若出现 `import_*.bin`，说明导入本质是"App 读设备上的 bin"，root 下也可改走文件投放。）

**找「运行时数据真源」：直接反查进程打开的 fd，别一层层翻目录** ★
本次找学习库绕了远路（App 私有目录、`/sdcard/Android/data/<pkg>` 全翻过都没有）。一击命中的做法：
```
adb shell ps -A -o PID,NAME | grep -iE '<关键词>'          # ① 先确认「谁在写」——可能不是被测 App
adb shell ls -l /proc/<pid>/fd/ | grep -viE 'socket|pipe|anon_inode|/dev/|/system|/apex|/proc|memfd|dmabuf'
                                                          # ② 直接列出它打开的数据文件
adb shell head -c 16 <file> | xxd                         # ③ 明文 SQLite 头 = 53514c69746520666f726d6174203300
```
**两个反常识点**：
- **数据可能在「另一个进程」手里**：本次写入方是独立 APK `com.czltek.cataandroid`（不是被测 App），
  真源在 `/storage/emulated/0/cata/`（**外部存储**）⇒ 清 App 数据 / 卸载重装**都不会**动它。
- 别假设"数据在 `/data/data/<被测包>/`" —— 先反查 fd 再下结论。
⚠️ 快照里的 `local_state.json`（如 `{"deletedMaxIds":{},"clearedMaxId":-1}`）**可能不携带删除标记**，
而设备本地删除标记仍在 ⇒ **"导入能否恢复被删对象"是未知项，必须实测，不可推断**。
可复用脚本：`tools/restore_learning_baseline.py`（`--recon/--backup/--push --confirm/--verify`，内置"无 --confirm 拒绝写"）。

## 解除物理约束：**喂帧注入（首选，回归底座）** vs 照片常驻（验收可用）

### ⚠ 先分清 `su 0` 与 `adb root` —— 别用一次探测就否掉注入 ★

**实测教训（出入库秤 2026-10-13）**：只跑 `adb shell "su 0 id"` 得到 `su: inaccessible or not found`，
就对外写了"设备无 root、喂帧注入出局、只能物理呈现"。**当天下午补测 `adb root` 直接拿到 `uid=0`** ——
`ro.debuggable=1` 的设备 `adbd` 可 root 起，**根本不需要 `su` 二进制**（厂商精简掉了而已）。

| 探测 | 命令 | 说明 |
|---|---|---|
| 有无 `su` | `adb shell "su 0 id"`；`ls /system/{bin,xbin}/su` | 只说明"有没有 su 二进制" |
| **能否 root** | **`adb root` + `adb shell id`** | ✅ 真判据 |
| 最强信号 | `getprop ro.debuggable`（=1 基本必成）、`getenforce`（Permissive 更省事） | ✅ |

**→ 铁律：判"能不能注入"必须 `adb root` 与 `su 0` 都试；只试一个就下结论，会得出反向结论。**

### 真正的"三重否证"（三条都否掉，才能说"必须物理呈现"）

| 旁路 | 取证 | 否证信号 |
|---|---|---|
| ① frida 喂帧注入 | `adb root`；`adb shell id`；`ls /data/local/tmp` | 拿不到 uid=0 ／ server 推不进去 |
| ② `am start` 直启跳转目标页 | `am start -n <pkg>/<目标Activity>` | `SecurityException: … not exported from uid <appuid>` |
| ③ 接口注册/更新人脸 | 看注册 DTO 是否要**特征值 `byte[]`** | 需要 `[B`；且属写操作、会污染本地库 |

**顺带必做的两件事**：

1. **反编译拿"跳转链"，别靠猜**：从人脸页 `successJump()` 往下找 `const-class` 就能拿到目标页 ——
   实测 `lambda$successJump$2` 里并列出现 `MaterialByDocumentActivity`（入库）/ `OutByDocumentActivity`（出库），
   入口页读 intent 的 `flag` 分流。**知道目标页才能验证"是否真过了脸"**（断言前台 = 目标页，而非停在人脸页）。
2. 若确实只能走物理呈现，**先确认活体强度**：实测本设备活体检测 = **关闭**（设置页 `is_live=false`）。

### 喂帧注入 · 三个必须先量准的参数（量错白干）★

1. **hook 点要选"真正喂给识别服务"的那一层**：本设备 `CameraHelper.onPreviewFrame` **方法存在但从不触发**
   （走 `setPreviewCallbackWithBuffer` 的内联回调），有效点是 **`FaceScanActivity$4.onPreview(byte[],Camera)`**。
   判法：两个都 hook 上计数，看谁在跳。
2. **尺寸以识别服务的实参为准，别用总字节数反推**：实测 `requestFaceFeature(data, w, h, fmt)` → `720×544`。
   `816×480` 的总字节数**同为 587520**，但几何不对 → 稳定 `faces:0`（帧被压扁）。
   判法：hook 识别入口打印 `(len, w, h, fmt)`。
3. **格式码要对**：`2050` = ArcSoft `ASVL_PAF_NV21`（Y 全图 + VU 交错半图）。
   素材生成**别依赖 `cv2.COLOR_BGR2YUV_I420`**（OpenCV 5.0 有尺寸断言坑）→ **手写 BT.601**。
4. **构造 Java byte[] 别用 JS 数组**：`Java.array('byte', jsArray)` 造 587KB 实测 **10.2 秒**（不可用）；
   改 **base64 → `Java.util.Base64.decode` / `android.util.Base64.decode`**（瞬时），或 `Java.array('byte', Uint8Array)`。
5. **frida 连设备**：`enumerate_processes()` 在 Android 远程模式下**查不到 App 进程** →
   必须 `enumerate_applications()` 取 `identifier→pid` 再 `attach(pid)`。

### 注入是否真生效 —— 必须"溯源 + 对照"双证 ★

- **溯源**：注入回调里记录注入帧若干固定下标的字节值；识别入口对**同一批下标**采样比对 → 打印 `ours:true/false`。
  实测 `ours:true ×24 / false ×0` ⇒ 引擎吃到的**全是**注入帧。
- **对照**：**再注入一张纯灰无人脸帧**跑同一流程 → 应当"检不到脸、不过关"。
  两相对照、唯一变量是注入内容，因果才闭合。
- **别被"真人也在镜头前"蒙混**：先看截图里摄像头是否真有人 —— 有就必须做溯源，
  否则会把真人的通过算成自己的功劳。

### 物理呈现的落地件（一次摆好，长期可回归）

| 件 | 做法 |
|---|---|
| 手机/平板全屏图 | 人脸铺满屏（`cover` 裁切），亮度拉满、关自动亮度 |
| A4 打印稿 @300dpi | 人脸占版面约 70%、带边框与距离/光线提示 |
| **PC 端全屏显示工具** | 显示器方案：全屏无边框置顶放照片（多屏可选），设备 **USB 外接摄像头对准显示器** → **摆一次、后续每轮回归无人** |

目标：让第 1/2 步无人值守。两条路，**先判定有没有 root + 能不能跑 frida**：

| 注入路线 | 结论 | 实测依据 |
|---|---|---|
| 虚拟摄像头 `v4l2loopback` | ✘ | `/proc/modules` 里没有该模块，`/vendor/lib/modules` 也无对应 ko；Android 终端基本不提供 |
| 让应用改从图片文件读 | ✘ | APK 内**无"文件图源"分支**；抓拍目录（`/sdcard/faceCheck/`）**只被写入、从不被读取** |
| USB 采集卡冒充相机 | ✘ | 应用走 **UVC 的 USB 设备枚举**取流并记 id（实测 `初始化手部相机 id=127`），换设备即对不上 |
| **frida hook 预览回调喂帧** | **✅ 已实测打通** | hook `CameraHelper.onPreviewFrame(byte[], Camera)`，`System.arraycopy` 把素材写进原 buffer → 人脸/手部/（体温）全部推进，**整流程零人工** |
| 改包 / `LD_PRELOAD` hook UVC | ◑ 技术可行 | root 下有 `setprop wrap.<pkg>` 注入这条路 |

> ⚠️ **两种路线的定位不同，别混**：喂帧注入**改变了被测对象的运行环境** → 结论只能作**回归流水线底座**（"流程可跑通"），**不能直接进验收报告**；验收侧仍要用**照片常驻**（打印粘贴/屏幕常驻）在**未改造**的设备上复核。这个区分必须在交付里写清。
>
> **怎么一句话判"算不算改造运行环境"——看输入走的是哪条通道**：
> - **产品对用户开放的通道**（触摸事件、界面控件）→ 换的只是"操作者"（人 → 脚本），产品仍**知情**（它知道有人点了它），**不算改造**。UI 驱动属此类，结论可按常规口径使用。
> - **产品内部的私有通道**（Java 方法调用、内存 buffer、传感器返回值）→ 喂进去的是产品**无从判别真伪**的数据，它仍以为自己面对的是真实世界 → **算改造**。frida 喂帧属此类。
>
> **同一种手段、两种身份，绝不能混**：
>
> | 测试目的 | 注入在这里的身份 | 结论效力 |
> |---|---|---|
> | 想让流程**跑通**（无人值守回归） | 作弊 / 替身 | 只能作**回归底座**：证明"流程可无人重复跑通" |
> | 想验证它**能不能挡住**（活体 / 防伪 / 反作弊） | **攻击手段** | 注入结果**本身就是真实缺陷证据**（实测：喂照片，人脸关 1.0 满分通过 → 活体绕过成立） |
>
> 判据：**被测对象的业务契约里，有没有"输入可能被伪造"这一条**。有 → 注入是合规的攻击面；没有 → 注入只是替身，别把它的通过当成功能通过。

### 喂帧注入实操（frida）—— 已实测打通，10 条要点

**0. 能跑 frida 的前提**：设备 root（工程 root `su 0` 即可）；**frida-server 版本必须与 RK 内核兼容** —— 实测 **17.x 在本机崩溃**（`frida_sigchain_compat_validate_signal assertion failed`），**降到 16.7.19 才稳**（客户端与设备端版本必须一致）。连接用 `add_remote_device('<设备IP>:27042')`，**别用 127.0.0.1**（adb daemon 一重启 forward 就丢）。

1. **找注入点 = 找"相机帧进 Java"的那个回调**，不是找相机驱动。实测人脸与手部**都走同一个** `com.face.faceidentify.camera.CameraHelper.onPreviewFrame(byte[] data, Camera)`（另一个 `CameraHandHelper` **实际未被调用**，别被类名骗了）。先用探针把 `data.length` 打出来：
   ```js
   C.onPreviewFrame.implementation = function(d, c){ console.log('len='+d.length); return o.call(this,d,c); };
   ```
   长度即 `W*H*1.5`（NV21）→ 反推分辨率（实测人脸 1024×768=1179648、手部 1440×1080=2332800）。

2. **改内容用 `System.arraycopy` 原地覆盖，绝不替换数组引用** —— 换引用会破坏 `Camera.addCallbackBuffer` 的归还机制，画面会黑/崩。
   ```js
   if (src && src.length === d.length) System.arraycopy(src, 0, d, 0, d.length);
   return o.call(this, d, c);
   ```

3. **素材按"帧长度"分派**，不要按阶段猜。同一进程里不同环节帧长不同，用长度做 key 最稳（`d.length===1179648 → 人脸`、`===2332800 → 手部`）。

4. **读素材别用 frida 的 `File` API**（运行时 `TypeError: not a function`）→ 用 Java NIO：`Java.nio.file.Files.readAllBytes(Paths.get(path, Java.array('java.lang.String', [])))`。
   素材先 `adb push` 到 `/data/local/tmp/<dir>/`（`chmod 666`）。

5. **NV21 素材生成**（OpenCV）：`i420 = cv2.cvtColor(bgr, COLOR_BGR2YUV_I420).reshape(-1)`；`Y=i420[:h*w]`、`U=i420[h*w:h*w+h*w//4]`、`V=i420[h*w+h*w//4:h*w+h*w//2]`；`vu = np.empty(h*w//2)`；`vu[0::2]=V; vu[1::2]=U`；拼 `Y+vu`。**注意 `vu` 长度是 `h*w//2`（不是 `empty_like(u)`）**，否则 `could not broadcast`。

6. **体温等传感器也得注**：`TemperatureBean.setBodyTemperature` 强制成合规值（实测无人时恒 35.0，真人体温 35.3~36.3）。**不加这一步第 1 步就卡住**（"没检测到体温无法推进"）。

7. **验证"引擎真的看到了你的照片"——用指纹，别靠肉眼**：`onPreviewFrame` 和提交识别的 `aiAutoRecognition` 之间可能隔着拷贝/旋转，**唯一硬证据是逐字节指纹相等**。
   ```js
   // JS 侧算 fp，Python 侧对素材文件算同样 fp，比对
   function fp(a,n){ var s=0; for(var i=0;i<n;i++) s=(s*31+(a[i]&0xff))%1000000007; return s; }
   ```
   实测 `[AI] 第1帧指纹 fp2000=925438867` ≡ 素材文件 `fp2000=925438867` → 注入确实到达引擎。
   > 别用"界面预览截图"判断注入是否生效 —— **预览 SurfaceView 走原生纹理，显示的是真实相机画面，与 Java 侧 buffer 是否被改无关**。

8. **埋点要挂在"真正在跑的那个类"上**：同一功能可能有两套界面（实测手部检测跑在 `FeatureActivity`，而另一套 `HandsCheckActivity` 是死代码）。**挂错类的表现是"hook 一个日志都不打"** —— 别据此判断"逻辑没执行"，先去 `dumpsys activity` 确认前台 Activity，再 grep 该类是否含目标字符串。
   ```
   adb shell dumpsys activity activities | grep -E 'ResumedActivity'
   ```

9. **frida 里直接调 AIDL 对象的 getter 会 `TypeError: not a function`** → 改为 **hook 该 getter 把返回值采集到数组**，再打印数组。这条对 `Parcelable`/binder 结果类基本通用。

10. **找"通过判据"最省力的方法：反编译直接读判定方法**（androguard 纯 Python 可用，无需 jadx）：
    - `get_strings()` + 遍历方法取 `const-string` → 定位"某个提示语属于哪个方法"
    - 自写 `dex_dump_method.py` 打印方法**完整 smali**（含分支目标）→ 直接读出 `if (countCode(list,'zhangxin') >= targetNumber)` 这种判定式
    - 枚举值**运行时读**更保险：`Java.use('...').HANDS_PALM.value.code.value`

11. **识别引擎可能"只认冷启动后的首次进入"——复跑前先 `am force-stop`，否则喂到死也过不去** ★★
    实测（出入库秤人脸，2026-10-13 二次复跑）：**非冷启动**再次进入人脸页时，注入照常在跑
    （`inject n` 涨到 560+，帧确实被替换），但 `detectFaces` / `compareFaceFeature` **一次都不调用**
    → 永远过不了脸；同一张帧在 **`am force-stop` + monkey 冷启动后首次进入** 时立即
    `faces:1 → score=1 → SUCCESS-JUMP`。
    - **判据：看"引擎方法调用次数"，别只看"注入计数"**。`inject n` 在涨 ≠ 引擎在工作——那只能证明
      `onPreview` 被调，不能证明识别管线启动。
    - **另一个佐证：截图里是真实摄像头画面**（预览 SurfaceView 走原生纹理，与 Java buffer 被改无关，见第 7 条）
      → 一旦发现"帧在替换、引擎没动静"，先冷启动再说。
    - **实践**：把 `force-stop → monkey 启动 → 点入 → attach 注入` 写成固定前奏（约 12s），别复用上一次的页面状态。

12. **App 已在前台时 `am start` 不会"回到首页"——它只把 intent 派发给顶层实例** ★★
    实测（出入库秤，2026-10-16）：停在 `MaterialByDocumentActivity`（带相机预览）时执行
    `am start -n <pkg>/<MainActivity>`，设备回
    「Warning: Activity not started, intent has been delivered to currently running top-most instance.」
    → 前台仍是原页面，后续"回主界面 → 点入口"的动作**全部踩空**（pytest 里表现为"目标页未加载"，
    且因为原页面是持续重绘页，`uiautomator dump` 同时报 `could not get idle state` → 极难定位）。
    - **正确前奏**（任何"从主界面重走一遍"的用例都要）：
      `am force-stop <pkg>` → `am start -n <pkg>/<MainActivity>` → 等 5~6s 落主界面。
      和第 11 条的人脸冷启动铁律**用同一招，一次做对两件事**。
    - **别指望 `monkey -p <pkg> -c LAUNCHER 1` 重启**：App 活着时它同样只是把 launcher intent
      派发给现有实例，进程不重建。
    - **自检**：冷启动后先打 `dumpsys window | grep mCurrentFocus`，确认落在主界面 Activity 再往下点。

### 素材从哪来：**优先翻设备自己的历史成功帧**（比重新拍强得多）

设备会把**每次通过时提交的原帧**存下来（实测 `/sdcard/faceCheck/*.jpg`，164 张，其中 11 张正是手部帧）。**这是"标准答案"** —— 直接拉下来、还原成 NV21 回喂即可。
```bash
adb shell "su 0 tar cf /data/local/tmp/fc.tar -C /sdcard faceCheck"   # 用 tar 一次拉，比逐张 pull 快得多
```
- **按分辨率分类**判类型（实测 768×1024=人脸、1080×1440=手部）
- 落盘可能带旋转 → **生成多方向候选（rot90cw / rot90ccw / letterbox / crop）逐个实测**，别猜

### 为什么"用户手机拍的照片"会失败：**画质无关，视角/构图才是判据**

实测：同一张照片，人脸环节识别分 **1.0（满分）**，手部环节引擎**逐帧返回 `zitaicuowu`（姿态错误）**，一个"手掌"都不给 → 永远不推进。
- 手机"举着双手对镜头拍" ≠ 设备"俯视看台面平摊双手"
- 设备要的是**俯视、双手平摊、放在导引垫上、背景干净**
- **实测关键：内容不旋转地等比缩放居中（letterbox）能过；rot90cw / rot90ccw 全被判姿态错误** —— 说明引擎对**画面朝向**敏感，换素材时**方向必须当变量逐个试**

> 判定"是不是素材问题"的干净方法：把链路拆成 **注入是否到达**（指纹）→ **引擎返回什么码**（hook 结果对象）→ **App 判定条件**（反编译）。三者一列，"照片问题 / 链路问题 / 逻辑问题"立刻分开。

**唯一现实解法（验收侧）：让真实相机"看到"照片** —— 即把"人举照片"改成"**照片常驻在相机视野里**"，一次布置、整趟无人：

| 方式 | 做法 | 评价 |
|---|---|---|
| **打印粘贴（首选）** | 素材排一张 A4（人脸 + 手心 + 手背 + **虚线裁剪框**），剪下后：人脸照**支在取景框正前方约 40cm**（硬纸板立起来），手部照**平铺在相机正对的台面** | 无反光、不闪屏、无需供电，**比举手机更稳** |
| 屏幕常驻 | 平板/显示器摆进相机视野，内容用脚本控制切换 | 便于**换人换素材**（多轮回归） |

排版脚本要点：A4@300dpi（2480×3508）、`ImageFont.truetype('C:/Windows/Fonts/msyh.ttc')` 写中文、虚线画裁剪框。
> ⚠️ **`cv2.imread` 读不了中文路径**（**静默返回 None**，不抛异常）→ 一律 `np.fromfile + cv2.imdecode`。

> 手部两张（`personHandFront` / `personHandBehind`）实测是「手部检测通过」**前后各一张**（14:08:03 与 14:08:07，间隔 4s，中间就是"通过"）→ 不像要求换姿势，**台面先放一张试**，省一轮换图。

### 但**别急着做物理呈现** —— 先翻设备上的原厂调试资产（实测捡到宝）

内网测试机 / 工程样机常留着原厂调试件，**`/data/local/tmp` 是第一现场**，先 `ls` 一遍再决定方案：

| 找什么 | 实测捡到 | 价值 |
|---|---|---|
| **能"吃图片文件"的算法工具** | `asdk_demo/asdk_demo_tool`（掌部算法包，`read_mode: FILE`、`format: IMAGE`） | **零物理件**复跑生物识别算法、直接出判定 ⇒ 比布置场景干净得多 |
| **注入先例** | `asdk/libfakecpuinfo.so` + `fake_cpuinfo` + `patched.fp` | 证明**本机 LD_PRELOAD 注入可行** ⇒ "能不能做喂帧注入"看这个就知道 |
| 厂商实测素材 | `pull_images/real_0*.jpg`、`bmks/*_hand.jpg`（`<id>_<时间>_<设备号>_<流水>_hand.jpg`） | 原厂"拉照片离线复跑"的现成做法，直接照抄 |
| root 形态 | `/system/xbin/su`（suid），`adb shell id` → **uid=0** | 工程 root（非 Magisk），adb 即 root，免 su 提示 |
| 自动授权 | `grant_usb.dex` | 免手工点"允许访问 USB"弹窗 |

**离线算法工具的两个通用坑**：

1. **必须显式 `LD_LIBRARY_PATH=<副本目录>`** —— 复制出来的目录若不自带库路径，会去加载**系统同名库**（实测 RGA `v1.7.5` vs 目录内 `v1.10.0`）→ `rknn_init error, ret=-1`，看起来像"模型坏了"。
2. **交互式入口会"假跑完"** —— 不传参数时它打印「输入图片路径」后**读 stdin**；stdin 空 → **立刻退出且 exit=0**，日志看着完整但**零推理**。对策：**把图片路径/目录作为命令行参数**传进去。

> 判据读法：汇总里的「检出目标总数」常 **> 图片数**（逐手/逐目标检测，一张双手照 = 2 个目标）。**别把"目标数"当成"图片数"**，混淆了会误判规模。

### 接上一层：把「喂帧注入」与「UI 驱动」拼成一条链（混合编排）

两层的**能力边界互补**，别指望一种手段包打天下：

| 层 | 负责的步骤 | 手段 | 是否改造被测对象 |
|---|---|---|---|
| A 喂帧注入 | 生物识别等**物理环节**（人脸 / 手部 / 体温） | frida hook 相机回调 | **是** → 只能作回归底座 |
| B UI 驱动 | **交互环节**（答题 / 选项 / 提交） | `adb input tap` + 模板匹配 | 否 → 结论可按常规口径用 |

**衔接点选"界面状态"，别让两层共享内存**。实测最省事的就是**判步**：流程页有一条随步数等距移动的绿线，用它的几何高度反算 `step`，B 层 `wait(step >= N)` 接手即可。好处是两层可独立运行/调试，任一层挂掉都会在此**显性超时**，而不是"悄悄跑偏"。

**编排 = 一条 shell 串两个进程**（已实测跑通五步全流程、端到端 76s）：

```bash
1) force-stop + logcat -c                              # 干净起点
2) run_frida.py inject.js --spawn --timeout 600 >log 2>&1 &   # 后台常驻注入链
3) 轮询主页按钮成熟(NCC>阈值) → input tap <中心坐标>     # 必须"成熟再点"，淡入期点击会被吞
4) e2e_driver.py run --live --attach                   # UI 层接手第 3/4 步
5) 收尾截图 + 归档 frida 日志 + kill 注入进程
```

**给 UI 驱动加 `--attach` 时必踩的两个坑**：
- **绝不能 `force-stop`** —— 会杀掉已被注入的进程，注入链当场作废；
- **绝不能 `logcat -c`** —— 会抹掉注入链日志，事后无法复现。
- 顺手把"阶段 0-1（归零/进页）"与"阶段 2+（等待/作答/提交）"**抽成同一个方法**给两条入口复用；否则自行归零与外部接管两条路径的判步逻辑会分叉。

**断言必须按进程归因**：设备上常驻的**第三方预装组件**可能一直在崩 —— 实测 `com.iflytek.speechcloud:bdservice_v1`（vendor 预装、`targetSdk=8`、引用了 Android 9 起已移除的 `org.apache.http.*`）**每 6 秒崩一次、无限重启**，与被测应用毫无关系。直接把 `FATAL EXCEPTION` 总数当"崩溃数"会**长期误报**，必须过滤 `Process: <被测包名>` 再计数（实测同一趟：全设备 17 条 / 被测进程 0 条）。

## 称重/计量类物理约束：**串口帧注入**（与摄像头喂帧并列的第二类）★

带秤的设备（出入库秤、结算秤、体脂秤）里，「重量」是**第二类物理约束**：摄像头能喂帧，**重量同样能喂帧** —— 只要找准串口解析入口。实测（出入库秤 2026-10-13）：**定位 10 分钟、一次注入成功、入库全流程无人值守闭环并真实写库**。

### 1) 先定位"重量从哪来"（三步查，别猜）

```bash
# ① 谁占着串口
adb shell "lsof | grep -i tty"     # 实测：com.ali.shcema 持有 /dev/ttyS1
# ② App 里哪个类开的串口 → 反查常量 "/dev/ttyS1"
#    → MaterialByDocumentActivity.initSerialPort()
# ③ 收帧回调是谁 → 反查日志字符串「串口收到 / 串口打开成功」
#    → MaterialByDocumentActivity$18.onDataReceived(byte[])
```

> ⚠ **别被"内嵌厂商 SDK"带偏**：本机内嵌 `com.czltek.cataandroid`（CATA），名字像称重 SDK —— 实际它**只是服务保活壳**（healthChecker/FpsCounter），**没有任何 getWeight/onWeight**。重量是 App **自己读串口**。判断依据：dump 该类方法表，找得到 `onBind/startService/isStarted`，找不到任何重量 API。

### 2) 协议别硬猜：**先抓一帧真实的**

多数 App 会把原始帧打进日志（本机：`串口收到 hex=0A0D203030303030 ascii=00000`）：

```bash
adb logcat -c; sleep 4; adb logcat -d | grep -a "串口收到"
# → 8 字节帧：\n \r 空格 + 5 位十进制数字
```

抓不到日志就 **dump 收帧方法的字节码**，看长度判定 / `parseInt` / 除数常量：

```
hex(data).length()==16  →  Integer.parseInt(ascii.trim())  →  weight = 值 / 1000.0
                                   常量 4652007308841189376 = double 1000.0
```

> 坑：**除数常量是 double 的位模式，不是可读数字** —— 必须 `struct.unpack('>d', struct.pack('>Q', v))[0]` 解，别口算（本次口算把 `1000.0` 算成 `640.0`，差点构造错帧）。

### 3) 注入：hook 收帧回调，替换帧内容

```js
var C = Java.use("com.ali.framework.view.activity.MaterialByDocumentActivity$18");
var orig = C.onDataReceived;      // 真实帧仍走原链路，只是数据被换掉
C.onDataReceived.implementation = function (data) {
    return orig.call(this, FAKE);        // FAKE = \n\r + String(kg*1000).padStart(5,'0') 的字节
};
```

- **双证**：① 设备日志出现我们喂的值（`ascii=10000`）② 界面重量/金额随之变化（0 → 10kg / 10.00 元）
- ⚠ `orig.call(this,x)` 调原实现**不递归**（与喂帧注入同）
- ⚠ **后台进程生命周期**：`run_frida.py ... &` 起在某个 Bash 调用里，**该调用一结束就被杀**。注入与点击必须写在**同一次执行**中，否则会出现"我明明注入了、界面却是 0"的假现象（本次踩过）。

### 4) 流程里的**校验顺序**（踩过才知道，别只喂重量）

「完成验收」连续被拦三次，拦截顺序是固定的：

```
请先选择物料  →  请先拍照  →  （重量 > 0）  →  才能加入订单
… 加入订单后仍需在「查看入库单」里点「确认入库」才真正写库
```

⇒ **自动化必须按业务顺序补齐前置动作**（该点拍照就点拍照），不能只注入重量。查法：hook `Toast.makeText` 打印文本 + hook 关键方法打印 `orderItems/weight/仓库` 状态快照，一次点击就能看清卡在哪一环。

> ⚠ **按钮坐标必须从"运行时 View 树"取，不能从截图估算**（2026-10-13 复跑踩坑）：本类页面持续重绘，`uiautomator dump` 必报 `could not get idle state`，改用 **frida 遍历 decorView** 拿 `id + rect`（`dump_view.js`）。截图估算偏 26px 即落空，**而且会让后续每一步整体错位** —— 本次症状是"点完成验收后莫名回到首页"，实为早前一步没点中、后续点击落到了首页卡片上。实测精确点：`btn_camera(1598,662)` / `btn_pass(1052,968)` / `btn_detail(1707,398)` / `btn_verify(1725,402)`。
> ⚠ **成功弹窗有时间窗**：验收完成弹窗带 **6s 倒计时**（实测首次弹出 6s、观察到时已剩 4s），窗内的「查看入库单」**直接进入入库单确认页**；超时弹窗自动关，之后的点击就会落到别的控件上 —— 这是"时有时无"类诡异现象最常见的来源。错过窗口就改走**顶部「查看入库单」入口**（入库 1658,61）。

> ⚠ **View 树也拿不到时的兜底：用像素定位实心按钮** ★（2026-10-16 实测，`dump_view_any.js` 返回 `dumped:0`、`uiautomator dump` 又因相机预览必失败时救场）
> 直接用 PIL 扫图找控件：在候选 ROI 内按行统计"品牌蓝**实心**像素"数，取**最长连续行段 = 按钮 bounding box**，再在该行取蓝色 x 的 min/max。
> ```python
> def blue(x,y):
>     r,g,b = px[x,y]; return b>180 and r<110 and g<150      # 实心按钮蓝（区别于浅蓝描边/浅底）
> ys = [y for y in range(300,750) if sum(1 for x in range(1350,1900,4) if blue(x,y))>100]
> # 最长连续段 → 中心 y；再在该 y 上 scan x → 中心 x
> ```
> 实测精确命中：入库工作台「拍照」(1598,661) / (1598,565)、「完成验收入单」(1052,967)、「确认入库」(1750,982)。
> **口诀**：先 `wm size` 核对（本机 Physical **1920×1080**，截图同尺寸 **无缩放**，`screencap` 坐标 = 设备坐标），**别再脑补缩放比**——本轮一度按"显示比例"换算，把拍照按钮算成 y=662→668，实际按物料分支在 **565**，导致点击静默落空。

### 6) 同一功能有多分支时：**分支差异要一支一支量，别拿一支的坐标套另一支** ★

实测（出入库秤「货品入库」左导航 `按单据入库` / `按物料入库`，同一 `MaterialByDocumentActivity` 下两套视图）：

| 差异点 | 表现 |
|---|---|
| 按钮坐标 | 拍照 **662 vs 566**（同一 `btn_camera`，两分支 y 不同）；`btn_pass` / 确认入库 相同 |
| 前置动作 | 按单据：单价由单据带出、不可改；按物料：**必须手输**（点单价弹自定义对话框 + 系统键盘） |
| 同名弹窗按钮 | 「查看入库单」在按单据统计**直接进确认页**；按物料**只关弹窗**，需再点顶部入口 |
| 串口注入点 | 入库两分支**相同**（都走 `MaterialByDocumentActivity$18.onDataReceived`）；但**跨 Activity 会变**：出库分支是 `OutByDocumentActivity$19.onDataReceived`（同一 App、同一 `/dev/ttyS1`，但各自 Activity 有自己的回调内部类）→ **必须逐页实测确认**，别把 `$18` 抄到出库页 |

**出库双分支对照（2026-10-14 实测补全，同 `OutByDocumentActivity` 下两套视图）**：

| 差异点 | 按单据出库 | 按物料出库 |
|---|---|---|
| 入口路径 | 列表「详情」(1714,418) → 明细行「出库」(1725,422) | 左侧「按物料出库」(132,507) → 工作台「点击选择物料」(526,292) → 卡片「选择」 |
| 工作台 `btn_camera` 拍照 | **(1605,590)** | **(1605,494)** ← 同一按钮两支不同，**必须分别取** |
| 「加入出库单」`btn_add` | (1052,988) | (1052,988) ← 相同 |
| 确认页单价列 | 0.00元（单据未带价） | **带出物料档案价**（实测洋葱 2.00元 × 0.50 = 1.00元） |
| 注入重量上限 | ≤ 该料剩余库存 | 同（服务端才校验，见 F-3） |

⇒ **逐一 dump 坐标、逐一走一遍**，别假设"同一 Activity 就是同一套坐标"。

> ⚠ **绝不能用"页面标题"判断当前在哪个分支** —— 实测**按单据出库工作台顶部标题误写「按物料出库」**（左侧导航高亮才是对的，且按物料工作台顶部根本没标题），入库成功页标题也误写「完成出库」。**标题文案本身就是缺陷**，不能当判据。判分支只认：**左侧导航高亮 / 进入路径 / 当前 Activity**。
> （注：上述两处文案缺陷已于 **V07.11.001**（2026-10-16）修复确认——但"不拿标题当分支判据"这条纪律照旧：判据一旦依赖可被改版影响的量，下次改版就会再失效。）
>
> **UI 文案类缺陷的证据三件套（可复用，10 分钟出铁证）**：
> 1. **路径链** —— 把「进入前的页面 → 目标页面」相邻截图连起来。进前页标题是对的、目标页标题变了 ⇒ **排除"继承上一页"**（实测：明细页写「按单据出库」，进工作台变「按物料出库」）。
> 2. **相邻对照** —— 同进程内间隔 1 分钟分别进两个分支，**唯一变量=分支** ⇒ 排除"标题是固定栏位"（实测按物料工作台顶部**空白**，按单据那页才有字）。
> 3. **像素量化**（`tools/px_check.py`）—— ① 左侧导航高亮项取块中心均色：高亮≈`RGB(54,148,255)`、未选≈`(230,234,238)`，**互斥可判**；② 标题 ROI 内"蓝色文字像素数"：判据 `(B-R)>40 且 B>120`。
>    实测 3 张按单据截图该值**恒为 2176**、2 张按物料**恒为 0** —— **同一数值在不同截图里重复出现**，就是"同一段写死的固定文案"的硬证据，比肉眼看图强得多。
>
> **反向用法：缺陷修复后的"回归确认"（2026-10-16 实测，V07.11.001 修 C-1/C-2）**
> 判断"研发说修了、到底修没修"用同一套手法反向跑：
> 1. **先看包有没有真的换**——`dumpsys package <pkg> | grep lastUpdateTime`（实测 09:19:33 换包）+ `versionName`，**别信口头**；
> 2. **重走原缺陷路径**，逐分支各来一遍（C-1 走 按单据 + 按物料 两个入库分支；C-2 走按单据出库工作台）；
> 3. **原来的"自相矛盾"必须消失**——C-2 原来"左导航=按单据、标题=按物料"，修复后二者一致；
> 4. **相邻对照仍在**——按物料工作台依旧"无标题"，说明标题是按分支区分的、不是被写死成另一种错误；
> 5. 结论只写二值：**已修复 / 未修复**（附成功页截图 + 接口回执 + 单号）。
> **顺带扫同源面**：文案套错常是"同一套模板驱动多个页面"，修一个要建议研发全量扫其余标题（查询页/各成功页）。

**更危险的一层：多分支的校验强度可能不一样，弱的那支会把失败"静默化"。**
- 按单据支有「数量必须大于0」闸门 → 重量没注入进去会被拦住（失败是响的）；
- 按物料支**没有这道闸** → 重量为 0 也照样弹「验收完成」、照样能点「确认入库」，
  最终落一张「**数量 0 / 小计 0**」的单（实测踩到，见 `recon/入库双分支全流程覆盖_2026-10-13.md`）。

⇒ **断言不能只看"弹窗文案 / 是否走到成功页"**：
1. 提交前核对**业务恒等式**（数量 × 单价 = 小计，且 = 页面重量 × 单价）；
2. 提交后查**网络回执**与落库字段（`number / price / totalPrice`），两者都要对。

### 5) 成功判据 = **网络层写入回执**（最硬）

```
POST /app/inventory/addInStorageSingle → {"msg":"入库成功"}
POST /app/inventory/confirmInStorage   → {"msg":"确认入库成功"}
```

只看到界面 Toast 不算数，**必须抓到 200 + 业务码 + 单号**（本次：`CG2026101316495505537` / 入库 10.00 斤 / ¥10.00）。

> **取回执最省事的通道：直接 grep App 自带的 `okhttp.OkHttpClient` 日志**（2026-10-14 实测）。
> 不少终端 App 未做日志脱敏，`logcat` 里就有**完整请求行 + 响应 JSON 全文**：
> ```
> adb logcat -c ; <点提交> ; adb logcat -d | grep -a "okhttp.OkHttpClient"
> I okhttp.OkHttpClient: --> POST http://<host>/app/inventory/addInStorageSingle
> I okhttp.OkHttpClient: {"msg":"入库成功","code":200,"data":419}
> I okhttp.OkHttpClient: {"msg":"查询成功","code":200,"data":{"outboundId":176,"outboundNumber":"CKDD...","number":5.00,...}}
> ```
> 比 hook 网络层/抓包更完整（**响应体全文含 `depositId`/`outboundId`/`number`/图片URL**），且零额外脚本。
> ⇒ 先 `logcat | grep -i okhttp` 试一次，**有就直接用，别急着上 frida**。

### 6) 界面 dump 失效时的替代（本类页面高频）

这类页面**持续重绘**（串口每 ~100ms 刷一次重量）→ `uiautomator dump` 报 `ERROR: could not get idle state`、dump 为空。
替代：**用 frida 遍历 `decorView`**，输出每个 View 的 `id 名 / text / getGlobalVisibleRect` 坐标 —— 既拿到精确点击坐标，也能一眼看出"哪些容器/按钮是隐藏的（rect 全 0）"，比截图目测靠谱得多（本次靠它把 7 步的坐标全部量准）。

> ⚠ **dump 可用性是"逐页分裂"的，别一刀切**（出入库秤 2026-10-14 实测）。同一台设备上：
>
> | 页面 | `uiautomator dump` |
> |---|---|
> | 主界面、出库列表页、出库明细页、**出库·物料选择页**（`rv_material_out_select` 卡片网格）、查询三子页（查货品/查明细/查仓库） | ✅ **可用**（能拿到 `btn_*` / `tv_material_*` 的精确 rect） |
> | 入库/出库的**工作台**与**订单确认页**（串口持续刷重量、持续重绘） | ❌ 失效（`could not get idle state`，或 dump 为空） |
>
> ⇒ **不要因为"某页 dump 失败"就全流程改用截图估算**；先花 30 秒试一次 dump，能用就用（比截图换算准得多）。反过来，工作台页别浪费时间试 dump，直接截图换算（截图 px × 设备宽/截图宽）。
>
> **frida dump 必须按具体类名 `Java.choose("<Activity 全名>")`**：写通用版 `Java.choose("android.app.Activity")` **匹配不到实例**（实测只回 `{"tag":"dump-complete","dumped":0}`）→ 一页一个脚本最稳。另注意 dump 脚本里的类名**写死了就只对该页有效**（曾把入库页类名拿去 dump 出库页，只得到 `dump-complete` 无控件，差点误判成"页面不可 dump"）。
>
> ★★ **更危险的是：通用 `Java.choose("android.app.Activity")` 一旦真匹配到实例，会直接 SIGABRT 杀掉 App**（2026-10-16 实测，出入库秤）：
>
> ```
> Abort message: 'JNI DETECTED ERROR IN APPLICATION:
>     a thread (tid 9184) is making JNI calls without being attached
>     in call to DeleteGlobalRef'
> signal 6 (SIGABRT) ... fg TOP ... Process com.ali.shcema has died
> ```
>
> 根因：`Java.choose` 的回调跑在 **frida 自己的线程**（未 attach 到 JVM），在回调里调 `View.getGlobalVisibleRect()` / `getText()` 这类 JNI 方法即触发 ART 检查 → abort。
> **后果极具迷惑性**：App 已死，但 SurfaceFlinger 保留最后一帧 → 之后两次 `screencap` 得到**字节完全相同的 PNG**，
> 排查时会被读成"点击无效 / 页面卡死"，白绕一大圈。
> - **处置**：把 View 树 dump 视为**高危动作**（跑一次就可能杀一次 App）；能不用就不用，
>   逐页写专用脚本（按具体 Activity 类名 `Java.choose`）只在明确需要时跑，且跑完必须**重查前台 Activity**确认 App 还活着。
> - **判据速查**：`adb shell "ls -t /data/system/dropbox/ | grep data_app_native_crash"` 看时间戳，
>   与 Abort message 对得上就是它；`Foreground: Yes` + `pid` 可确认是前台 App 被杀。
>
> **xml 落盘位置**：`adb shell cat /sdcard/x.xml` 重定向时**别放 `/tmp`**（Git Bash 的 `/tmp` 与 Windows python 看到的不是同一路径，python 会 FileNotFoundError）→ 直接落到工程目录再解析。

### 崩溃定性：**先做对照实验，别急着报缺陷** ★

实机跑流程时遇到 App 崩溃，**第一反应不是"缺陷"，而是"我挂的这个 frida 会不会就是肇因"**。实测（出入库秤 2026-10-14）：

```
Fatal signal 11 (SIGSEGV), fault addr 0xe, tid 5842 (com.ali.shcema)
#00 pc ... /memfd:jit-cache (deleted) (com.ali...OutByDocumentActivity.bytesToHex+124)
```

**判读要点**：
- 崩溃帧落在 **`/memfd:jit-cache (deleted)`** = 执行的是**已被释放的 JIT 代码**。frida 改方法实现会让 ART 去优化/重编译，**这类崩溃在"挂着 frida 时"高发，与产品逻辑无关的概率很大**。
- 别只看一次日志就下结论，**做两组对照**：
  1. **不挂 frida**：`am start` 直接拉起该 Activity，静置 ≥30s → 记是否崩；
  2. **挂 frida**（走原本会触发的路径，如人脸注入）→ 静置 ≥60s → 记是否崩。
- 两组都不崩 ⇒ 判**偶发**，按 4 步确认（稳定复现/违反契约/跨证据一致/非环境抖动）**不达标**，只能留作观察项，**不进缺陷清单**；两组都能复现 ⇒ 才值得深挖。
- 顺带一条**工程红利**：能 `am start` 直达的 Activity（本机 `OutByDocumentActivity` 实测可直达）**可以完全绕开 frida 与前置步骤**，是做"干净对照"和快速复测的最佳通道 —— 同时也是**安全发现**（见下条）。

> **`am start` 直达 = 绕过前置认证的证据**：若某页在主界面要求先过人脸/登录才能进，但 `adb shell am start -n <pkg>/<Activity>` 能直接进入并完成全流程 → 说明**认证只做在入口 UI 层，Activity 自身无鉴权**。这是**客户端侧可独立复现**的条目（物理接触设备者可绕过），实测口径：直达后能否读数据 + 能否完成写操作。同时提示研发确认是否设计如此（后端若另有校验则风险降级）。

## 稳定性验证：**批量跑批 + 统计口径**（从"跑通过"变"可回归"）

单趟跑通只证明"能跑"，**证明不了"可重复"**。补稳定性的最小做法：**一条命令串行跑 N 趟 + 一个汇总脚本出统计**。

```bash
# 1) 批量跑批：token = state[:symptoms]，逐趟记 rc / 墙钟 / 证据目录 → runs.tsv
bash tools/stability_batch.sh normal normal normal leave:1 leave:2 leave:3 leave:4
# 2) 汇总统计：解析各趟 result.json → summary.md / summary.json
python tools/stability_report.py evidence_r13/stability_<ts>
```

**跑批脚本要点**：外壳**只做串行调度 + 记账**，不改任何驱动逻辑；每趟独立冷启（`force-stop` → spawn）、独立证据目录、独立日志；**一趟失败不中断**（继续跑完，最后按 rc 汇总失败率）。逐趟结算读 **进程退出码 rc**，别靠 grep 日志猜成败。

**统计口径（只报"通过率"是不够的）**：

| 指标 | 为什么必须报 |
|---|---|
| 通过率 | 基本盘。**样本 < 5 趟不要下"稳定"结论** |
| **墙钟 / 驱动时长（均值、标准差、极差）** | 只看均值会掩盖长尾；**极差**对现场最有说服力（实测分支内极差 ≤1s） |
| **分支间差异** | 差异要能归因到具体动作（实测 `leave` 比 `normal` 稳定多 6.5s = 「点离岗 + 症状区展开 + 勾选 + 选中态校验」的固定开销） |
| **随机化环节的分布**（如答题正解落位） | 别只写"通过"。**列出每题各选项的命中次数**才能证伪"位置固定"（实测 7 趟里第 1 题命中过 B/C/D 三种、答错数恒为 6 → 坐实"正解随机、必须试错"） |
| **被测进程崩溃数** | 必须**按 `Process:` 归因**（见坑清单），不要用"全设备崩溃数"当结论 |
| 环境前置项 | 每趟开跑前查 **frida-server 在不在 + 后端配置对不对**（见坑清单"隔天复跑的环境漂移"） |

**产出物**：`runs.tsv`（逐趟账面）+ `summary.md`（可直接贴报告的表）+ `summary.json`（机读，便于后续画图/回归对比）。

## 坑清单（都是实测踩出来的）

| 坑 | 现象 | 对策 |
|---|---|---|
| **假通过（答题类专属）** | 脚本"点了 3 次 = 答了 3 题"就往下走，但界面**仍停在某一题、选项标红**（点击被收下了，题没通过） | **推进判据必须来自界面**（判步 / 下一题出现），**不能只数点击次数**。动作后加"页面就绪校验"，未就绪 → **中止**，绝不进入下一步 |
| **在错误页面上误点** | 前一步没过，脚本却按"下一步"操作，**误提交了一条错误分支的业务记录** | 每个阶段的**第一个动作前**校验"当前页确实是目标页"；不匹配立即中止 |
| **冷启动过渡帧** | 重启应用后定位分**骤降**（实测 0.90 → 0.57），低于阈值直接拒点 | 要求**连续 ≥2 帧命中**才算稳定（`wait_el`） |
| **渲染竞态** | 截图时**题干/选项还是空框**，标签已在位；点击侥幸成功 | 点击前追加"文字已渲染"判据；至少把这种帧单独存档 |
| **按钮跨态串位** | 模板在**邻居控件**位置得高分（实测 0.933） | 按控件矩形切分 `roi`，左半/右半各搜各的 |
| **静默失败** | 点了按钮**界面无变化、无 Toast、零网络请求** | 别只看界面！**查应用进程日志**。⚠️ 但**先排除"必填前置未满足"再看成缺陷**（见下一行）—— 这个坑实测踩过一次 |
| **必填静默拦截** | 缺必填项时点提交：界面不动、零日志、零提示 | 正确结论是**「校验正常 + 提示缺失」的体验问题**，**不是功能缺陷**。定性前必须自问：**该动作有没有必填前置？**（先选某状态 / 先勾某项）。切开方法：**补上必填再点一次**，若成功 → 校验正常；若仍无响应 → 才是缺陷 |
| **校验用 Toast 提示 = 看着像"零提示"** ★ | 点提交后**页面纹丝不动、零网络请求**，据此差点判"按钮失效" | 校验**确实提示了**，只是 Toast 一闪而过（1~2s）。★ **判据：`logcat` 里出现 `[Toast#0]` 与 `NotificationService: Toast already killed. pkg=<包名>` ⇒ 一定有 Toast 弹过**（Toast 文本**不进 logcat**，必须截图抓）。实测实例（出入库秤 2026-10-16，按单据入库）：单价为 0 时点「确认入库」→ Toast**「物料「脉动」单价必须大于0，请先设置单价」**，**不发请求**；连点两次、页面静止到**两次截图字节完全相同**，极易误判成"页面卡死/按钮失效"。补填单价后立刻成功（`addInStorageSingle`→200 / `confirmInStorage`→200）。**⇒ 别急着判缺陷，先去抓那个一闪而过的 Toast。** |
| **同一表单控件在不同子模式坐标不同** | 两分支同一按钮，一个点得中一个点不中 | 实测同一 Activity 内：入库「拍照」按单据 `(1598,662)` / 按物料 `(1598,565)`（差 97px）；「单价区」按单据 `(635,558)` / 按物料 `(663,552)`。**坐标一律按当前子模式取，禁止跨子模式复用**；点了没反应时，先怀疑坐标落在控件外侧空白（实测点 `(533,556)` 落空、`(635,558)` 命中） |
| **淡入期点击被吞** | 控件有淡入动画，**形状已命中（NCC 够）但颜色还淡**，此时 `tap` **不生效** | 加**成熟判据** + **点击闭环**（见第 2 步）。只靠 NCC 判定会在不可点的淡态就点下去 |
| **同名分支差异** | 同一按钮、同一坐标、同样满分，一个分支成功另一个失败 | **差异变量只有一个**时，断定业务校验；设计"改一个变量"的受控实验 |
| **观察窗口空跑（探活体/等人操作类专属）** | 点了"开始"后应用**秒级退回上一页**，判步仍给出假信号 → 整个观察窗在错误页面上白跑；且无人在场时**零帧**却会被判成"防住了" | ① 加**入场校验**：以"**相机/引擎真的在跑**"为入场判据（如日志出现 `Face Recognition:`/`Camera angle:` 增量），不达标则**重试点击**；② 加**无效趟分支**：`样本数=0 且 相机零活动` ⇒ 判 **"无效趟（无人在场）"**，**绝不可**输出"活体拦截"这类正面结论 |
| 只看界面就判成功 | 界面看着变了但没落库 | 一律双源 |
| **hook 挂了死代码类** | 埋点**一条日志都不打**，容易被误读成"这段逻辑没执行" | 同一功能常有两套界面（实测手部检测在 `FeatureActivity`，`HandsCheckActivity` 是死代码）。先 `dumpsys activity \| grep ResumedActivity` 确认前台类，再挂 |
| **预览截图判注入** | 界面预览里看不到注入的图，就以为注入失败 | 预览 SurfaceView 走原生纹理，显示**真实相机**画面，与 Java buffer 无关。判注入只认**逐字节指纹** |
| **素材方向没试全** | 换了"更好"的素材仍不过 | 方向/取景是**独立变量**：实测竖版内容 **letterbox** 能过，**rot90cw/rot90ccw 全不过**。素材必须**多方向生成 + 逐个实测** |
| **frida 直调 AIDL getter** | `TypeError: not a function` | 改为 **hook 该 getter 采集返回值**，再打印采集数组 |
| **注入链被 UI 驱动打断** | 混合编排时注入忽然全部失效 | UI 驱动的初始化里**绝不能 `force-stop` / `logcat -c`**（会杀进程、抹日志）。加 `--attach` 模式跳过归零段 |
| **崩溃数被第三方进程污染** | "崩溃数 17"看着像被测应用崩了 | 预装组件可能**持续周期性崩溃**（实测讯飞 `bdservice_v1`：周期恒定 **6.0~6.6s**；5 个独立窗口全部命中 —— 90s/15、112s/17、119s/18）。**必须按 `Process: <被测包名>` 归因**再计数 —— 否则同一脚本不同窗口会得到 **17 / 0 / 18** 三个数。判定该循环的**直接指纹**：`logcat -b events \| grep <子进程名>` → `am_proc_start` / `am_proc_died` **成对出现、间隔 ~6s** |
| **单窗口"周期性"被读成"持续性"** | 在一个 30s / 90s 窗口里看到同一种崩溃每 6s 一次、PID 每次都换，就写成"无限重启 / 24h 不间断" | **周期性 ≠ 持续性**。窗口内的周期只能证明"该窗口内在重复"，**证明不了"一直在重复"**。定性前**必须另取一个跨窗口对照样本**（换个时间点再采一次）；两次结果不一致 → 结论降级为"**间歇性**"，诚实补上"**触发条件未查明**"，**第 ① 步（稳定复现）判为部分满足 → 不许升级缺陷编号** |
| **反过来更错：单次"观察不到"就推翻现象** | 复跑一趟采到 0 条，立刻把结论从"持续"改成"间歇"，并删掉原定性 | **单次阴性 ≠ 现象不存在**（那趟只是落在**暂停窗口**里）。实测走了完整弯路：**17 → 0 → 18**，最终靠 **5 个独立窗口 + 90s 连续存证** 才定准为"持续周期性"。**样本量不足时先补采样、再改结论**；任何定性反转都**必留修订记录**（时间 / 依据 / 改了哪几节） |
| **`logcat -b events` buffer 有容量上限** | 拿 "buffer 里最早那条" 当现象起点（"从 13:11 才开始崩"） | 本机 events buffer 仅留 **~20 分钟** → 最早那条只是 **buffer 边界**、不是现象起点。要用 `ps -A -o PID,ETIME,NAME` 的 **ETIME 反推开机时间**，再结合多次采样判断起点 |

| **流程卡住被误判为"识别不过"** | 界面停在第 1 步（人脸取景页），就断定"人脸识别没通过" | 先分清**是识别失败，还是识别成功后的业务失败**。识别已通过的三个铁证：`RecognizeService: Result:0, :1.0`（满分）、`getCanteenEmployerInfo uuid:NN`（已拿到人员 ID）、TTS `speak: text=人脸识别成功`。三者都在 → 问题**不在相机/算法**。再看 `Request Succeeded:<msg>, :<接口路径>`：若 msg 是"未获取到…"之类，则是**后端查询失败**。实测踩过：设备 `PROJECT_SERVER` 指向了另一台后端 → 每秒重试 `getCanteenEmployerInfo` 返回"未获取到食堂员工信息"，界面卡第 1 步，**看着极像识别不过** |
| **隔天复跑的环境漂移** | 昨天整趟全绿，今天一跑就卡，怀疑"是不是改坏了" | 复跑前两条必查：① **frida-server 还在不在**（设备重启即消失，`su 0 ps -A \| grep fs16` — 不会自启）；② **设备后端配置有没有被改**（`su 0 cat /data/data/<pkg>/shared_prefs/*.xml \| grep -E "SERVER\|PORT"`）。实测两坑同时踩到：设备重启后 fs16 消失 **且** `PROJECT_SERVER` 从 `192.168.2.171` 被改成 `192.168.2.62` → 表象都是"卡在第 1 步"，根因各不相同，**先验环境再查代码** |

## 定位"静默失败"的方法（**顺序不能颠倒**）

0. **先查"必填前置"**（最容易跳过、也最容易误判）：问用户 / 读业务流程 / 做受控实验 ——
   这个动作是否要求"**先选某状态、先勾某项**"？
   **不满足必填时的"无响应"是预期行为**，此时"零日志"恰恰是应用**本地校验后直接 return** 的证据。
   → 判定口径：**「校验正常 + 缺提示」= 体验问题（挂 N 编号观察项，不判 FAIL）**，**不是功能缺陷**。
   （踩坑记录：曾把某分支"点提交毫无反应"初判为"按钮无响应"，实测补上必填项后提交即成功 → 翻案）
1. **锁定时间窗**：脚本日志给出动作时刻 → 换算到设备日志时间
2. **查该进程在该窗口内有没有日志**：无 Toast、无异常、无网络请求 = **静默**
3. **找同期对照**：同一动作在**另一分支**成功的记录（同坐标、同 NCC）→ 排除定位问题
4. **收敛差异**：把"成功 vs 失败"的变量缩到唯一一个
5. **过完第 0 步才定性**：必填已满足仍无响应 → 才是**功能缺陷**（违反契约）；必填未满足 → 只是缺提示
6. 按用户的双轨制挂 **C 编号候选**，缺独立复现时**不得升级为 D**

## 交付模板
```
1. 能力矩阵（步骤 × 可否自动 × 是否需要人）
2. 实机 N 趟结果（时间线 + 断言表）
3. 关键发现（含"看似成功实为失败"的反例）
4. 新增资产（驱动脚本 / 控件档案 / 模板）
5. 遗留与下一步（含"人工残留秒数"）
```

## 表单类写操作（新增/编辑物料等）—— 六个必踩的坑 ★

### 1) `adb shell input text` 送不进中文 —— 会被输入法改写
- 现象：设备默认 PinyinIME 时 `input text AutoTestMat` 落成 **`uto€而是他》`**（ASCII 被当拼音吃掉），
  字段看着"有值"实际是垃圾，后续断言全乱。
- 解法：`adb shell ime set com.android.inputmethod.latin/.LatinIME` → 英文即正常；
  **测完必须恢复**：`ime set com.android.inputmethod.pinyin/.PinyinIME`。
- 真送中文：ADBKeyboard.apk（广播注入）或 frida `setText`；**别用 `input text` 硬试**。
- 纪律：自动化测试数据统一用 **ASCII 名称**。

### 2) 软键盘弹出 ⇒ 弹窗整体上移，一次性校准的坐标立刻失效 ★
- 实测：同一弹窗，软键盘弹出后整体上移 **~285 px**，同一字段存在两套坐标。
- 点开"底部选择器"（分类/单位）时软键盘**自动收起** ⇒ 那之后的点击必须切回"无键盘"坐标。
- 稳妥做法：**每次 tap 前 dump 一次拿真实 bounds**（`EditText` 的 `bounds` 随键盘变化），
  或在用例里显式维护"有键盘/无键盘"两套坐标常量。

### 3) 带相机预览的页面 `uiautomator dump` 报 `could not get idle state`
- 根因：MJPEG 预览常驻重绘 → UI 永不 idle。
- 解法：先 `input keyevent 4` 退到**无相机页**（主页 / 设置子页）再 dump；该页只做截图 + 坐标点击。

### 4) 写操作的真源常常在**后端接口**（不是本地库）—— 抓 logcat 定源
- 实测：新增物料 = `POST /app/inventory/addMaterial`（**带 sign 签名**），
  成功后客户端**自动** `queryMaterial` 刷新左侧列表 ⇒ 列表数据源是后端，不是本地缓存。
- 断言优先级：**网络回执**（`{"msg":"操作成功","code":200,"data":<新ID>}`）> 界面计数。
- ⚠ **界面无删除入口**时（长按列表项被识别为单击，只做自动填充），写用例会留下**后端脏数据**
  —— 跑写用例前先确认后端清理手段。

### 5) 表单必测"必填全空"这一刀 —— 三合一判据
- 判定"校验真生效"要同时满足：① 弹窗**不关**；② 有 **Toast**（`logcat` 见 `Toast#0` <宽×高>）；
  ③ **未发出任何写请求**（logcat 里 grep 接口名计数 = 0）。
- Toast 文案抓法：**连点 N 次让 Toast 常驻**，再在**同一次 adb 往返内**抓屏：
  `adb shell "input tap X Y; input tap X Y; input tap X Y; screencap -p /sdcard/t.png"`。

### 6) adb 连续多次往返会被判超时（SIGTERM）
- 解法：多条指令**串进一次** `adb shell "a; sleep 1; b; screencap -p /sdcard/t.png"`；
  或逐条用 `timeout N` 包裹。串行 shell 同时把 5~10 次往返压成 1 次，是这类设备最有效的提速手段。

### 7) ★★ `uiautomator dump` 失败时会**静默返回上一个页面的陈旧 dump** —— 驱动层必修
- 实测（2026-10-16，出入库秤）：导航到**入库**选择页后 dump，拿回来的却是**出库**选择页的内容。
- 根因：`uiautomator dump /sdcard/_dump.xml`（该页 `ERROR: could not get idle state.`）**失败**，
  紧跟的 `cat /sdcard/_dump.xml` 于是读到**上一次残留的文件** —— 内容合法、含 `<hierarchy`、
  长度也够 ⇒ **所有"内容有效性"判据全过 ⇒ 静默返回陈旧页面**。
  ⚠ 比"直接抛异常"危险得多：你会**拿着别的页面的层级当真**去下结论（本次差点误判"该页卡片上有编码"）。
- 修法（三选一，推荐第 1 个）：
  1. dump 前先 `rm -f /sdcard/_dump.xml`；失败时 `cat` 会报 `No such file` → 走重试，绝不误采；
  2. dump 后校验 mtime 新鲜度（`ls -l` 时间戳在最近 N 秒内）；
  3. 解析 `uiautomator dump` 的 stdout，必须出现 `UI hierchary dumped to` 才算成功。
- 通用水位：**任何"读文件拿结果"的抓取都要先删旧文件**，"内容合法"永远不等于"内容新鲜"。

### 8) ★★ 视图树里有节点 ≠ 用户能看见 —— 判"可见性"必须做**像素检验**
- 实测（2026-10-16，出入库秤「选择物料」页）：`uiautomator` 明确给出
  `tv_material_code` 节点，**有 text（999 / 34567 / 09087 / 77554）、有非零 bounds**
  （如 `[608,494][638,522]`，30×28px，就在名称正下方），**但屏幕上完全是空白**。
- 判定方法（可复用，10 行代码）：
  ```python
  # 对 dump 给的每个 bounds，到截图里统计"非白像素"
  px = list(im.crop((x1, y1, x2, y2)).getdata())
  nonwhite = sum(1 for p in px if min(p) < 200)
  # 与已知可见的控件（如名称）做对照：
  #   名称区 674/2432 非白（最暗 26）  → ✅ 正常渲染
  #   编码区   0/840  非白（最暗 255） → ❌ 控件在但没画出来
  ```
  **必须拿一个"已知可见"的控件做对照**，否则无法排除"裁错位置/坐标空间不一致"。
  名称区能命中 ⇒ 坐标空间一致 ⇒ 编码区纯白就是真的没渲染。
- 常见成因：`visibility=invisible/gone`、`alpha=0`、**文字颜色=背景色（白字白底）**。
  三者 uiautomator 表现不同，但从用户视角结论一致：**看不见**。
- 反过来说：**别用"dump 里有这个字段"去证明"用户能看到这个字段"**。
  这条差异在**同一个 App 的不同页面**上就真实存在 —— 学习管理列表的「物料编码」列**可见**，
  而「选择物料」页卡片的编码**不可见** ⇒ 写缺陷/写用例前必须逐页实测，不能一页代表全 App。

### 9) ★★ 设备上的「运行态」绝不能做硬断言 —— 只软告警 ★（2026-10-16 踩）
- 实测：`test_algo_config_status` 硬断言「本地算法服务 == 已启动」，10-13 连续 3 轮通过，
  10-16 直接红：「未启动」。**看起来像功能回归，其实是设备运行态漂移。**
- 定位手段（**看事实，别看文案**）：
  ```bash
  # ① 端口到底有没有监听（十六进制！17339 = 0x43BB）
  adb shell "cat /proc/net/tcp /proc/net/tcp6" | grep -i 43BB
  # ② 服务进程在不在
  adb shell ps -A | grep -i "<service-pkg>"
  # ③ 设备啥时候重启的（运行态漂移的头号原因）
  adb shell uptime
  ```
  实测结论：设备当日 09:12 重启 → 服务**不随 App 冷启动自启、也不按需自启**，
  必须手动点界面的「启动算法服务」才拉起。**4 个时机全否**（冷启动/进设置页/进学习页/进配置页）
  才敢下"不自启"的结论 —— 别只测一个时机。
- **用例纪律**：
  | 断言对象 | 处理 |
  |---|---|
  | 契约性内容（地址、控件齐备、文案枚举） | ✅ 硬断言 |
  | **运行态**（服务启停、激活态、在线状态、清单是否为空） | ⚠️ **只记录 + 漂移提示**，硬断言会造成假告警 |
- 定性话术：**运行态漂移 ≠ 功能缺陷**。判断三问 —— ①界面有没有显式恢复入口？②状态位有没有如实显示？③是不是设备重启/授权过期导致的？三问皆是 ⇒ 记录为「观察项」，不进缺陷清单。

### 10) ★★ `am force-stop` 会连带杀掉**进程内嵌的服务** —— 前置条件与状态断言会互相矛盾 ★
- 实测：算法服务**内嵌在 App 进程内**（`com.ali.shcema` 进程同时监听 `17339`）。
  于是「为干净起点先 force-stop」的前置动作，**恰好把待断言的服务杀掉**：
  手工点按钮拉起 → 状态=已启动；跑用例（内部 force-stop）→ 状态=未启动。
- 排查手法（**受控实验，一次定论**）：
  ```bash
  # 起服务 → 查端口 → force-stop → 再查端口 → am start → 再查端口
  ```
  端口随 force-stop 消失 ⇒ 服务内嵌在该进程里。
- 纪律：**任何"前置 force-stop"的用例，都不能断言"某个服务处于运行态"** ——
  除非先用受控实验证明该服务独立于 App 进程。
- 这条同时解释了另一个现象：**"只读用例"也可能改变设备状态**（force-stop 本身就是状态变更）。

### 11) ★★ 弹窗按钮别用坐标 —— **软键盘高度随输入法变化，会整体失准** ★（2026-10-16 踩）
- 实测：`test_N13_cancel_no_side_effect` 连跑 3 轮**全红**，断言只写着「『取消』未关闭弹窗」，
  看起来像 App 的取消按钮失效。实际是**用例自己的坐标错了**：

  | 状态 | 「取消」真实中心 |
  |---|---|
  | 无软键盘 | **(934, 795)** |
  | 打字后（**PinyinIME** 弹出） | **(934, 616)** |
  | 用例硬编码（10-15 在另一套输入法下测得） | (939, 515) ← **差 101px** |

  根因链：输入法不同 ⇒ 键盘高度不同 ⇒ 弹窗上移量不同（PinyinIME 只上移 ~179px，假设的是 285px）
  ⇒ **按钮被压在键盘顶边**（键盘顶边 ≈619，按钮 y∈[589,644]）⇒ 坐标点击打到键盘上。
- **修复姿势（模板，直接抄）**：弹窗交互一律「**先收键盘 → 按 resource-id 实时定位点击**」。
  ```python
  def _center_of(page, rid):          # 每次重新 dump 取 bounds 中心，规避位移
      for n in page.tree(force=True).find_all(id_contains=rid):
          if n.center:
              return n.center

  def _hide_ime_if_shifted(driver, page):
      # ★ 用某个已知按钮的 y 当"位移标尺"（无键盘 795 / 被顶起 616）
      c = _center_of(page, CANCEL_ID)
      if c and c[1] < 700:            # 确实被键盘顶起过
          driver.shell("input keyevent 4")   # BACK 只收 IME，不关弹窗（已实测）
          driver.shell("sleep 1.0")

  def _tap_dialog_btn(driver, page, rid):
      _hide_ime_if_shifted(driver, page)
      c = _center_of(page, rid)
      driver.shell(f"input tap {c[0]} {c[1]}")
  ```
- **两个反直觉点**：
  1. **不能无条件按 BACK 收键盘** —— 键盘没弹时 BACK 会把**整个弹窗**一起关掉。
     所以要用"位移标尺"判断键盘是否真的弹着。
  2. `dumpsys input_method | grep mInputShown` 在 BACK 之后**仍可能返回 true**（这里是 `true`），
     不可靠 —— **以"弹窗是否回到未位移位置"为准**，比查 IME 状态更靠谱。
- **推广**：同一份"有键盘坐标"会同时污染多个动作（本例：取消 + 确认新增 + 各输入框）。
  改成 id 定位后，**一次修掉整组**（`_fill_required` 5 个字段 + 取消 + 确认）——
  别再逐个坐标去调，那是无底洞。

### 12) ★★ 写库用例按「跑完能不能自己回到原样」分三档，只有 A 档能批量跑 ★（2026-10-16）
> 场景：被问"写库那 N 条现在跑吗"。**别按"是不是写库"一刀切** —— 按**执行代价**分档。

| 档 | 特征 | 处置 |
|---|---|---|
| **A · 可自愈** | 每条 `try/finally` + 专属 `_revert()`；只用**专用测试物料/仓库**；不碰业务数据 | ✅ 可批量跑，可进回归 |
| **B · 留痕但不消耗一次性资源** | 落单/改库存，但**不改不可再生资源**（如消耗品、单据池） | ⚠️ 跑**一次**取证即可，别批量、别跑批 |
| **C · 破坏 / 产生不可回收数据** | 新增**删不掉**的记录（界面无删除入口）／整物料全删／依赖外部备份才能还原 | ❌ **默认跳过**；要跑必须单独授权 + 先备份 + 明确回收通道 |

- 判 A 档的硬证据：读代码确认 **`finally` 里真的回基线**，且物料/仓库 id 来自**专用测试配置段**（如 `conf/api.json` 的 `e2e` 段），不是业务数据。
- 判 C 档的两个典型信号：
  1. 系统**没有删除入口**（新增即永久垃圾）——跑一次就多欠一笔债；
  2. 删除粒度**粗于用例粒度**（"删该物料的全部学习记录"，而用例只想删一条）⇒ 不可精确回滚。
- ★ **纪律：写库层永不进稳定性跑批**。跑 1 轮就消耗数据，跑 N 轮会把消耗品/单据池耗光，
  到后面全是"假失败"（环境空了，不是 App 坏了）。
- ★ **若已经决定不清理历史垃圾数据，就更不该再制造同类数据** —— 这是跳过 C 档最直接的依据。
- 归档口径：写库执行结果**单独立文件**（如 `reports/r1_write_*.json`），
  **不要覆盖**只读全量基线快照，否则"只读全绿"的证据被写库的 skip/pass 混淆。

### 13) ★★ 「执行结果快照」必须防覆盖 —— 一次 `--collect-only` 就能毁掉全量基线 ★（2026-10-16 踩）
- **事故**：为了列 13 条写库清单，跑了一次 `pytest -m e2e_write --collect-only`。
  仅此一步，就把 13:14 归档的「98 passed / 14 skipped」全量基线快照
  **覆盖成了 `stats` 全 0、`cases` 为空**（因为快照写在 `pytest_terminal_summary` 里，**无条件**执行）。
  幸好 5 分钟前做过归档 `r1_full_result.json`，才能恢复。
- **根因**：`terminalreporter.stats` 在收集阶段没有任何 passed/failed，`_TEST_CONTEXT` 也是空的
  → 写出一个"合法 JSON 但内容为空"的快照。**看着像正常产物，实际是空壳**。
- **修复模板（两处都要）**：
  ```python
  def pytest_terminal_summary(terminalreporter):
      cfg = terminalreporter.config
      # 守卫 1：--collect-only；守卫 2：零执行（报错早退时也会走到这里）
      if cfg.getoption("collectonly", False) or not _TEST_CONTEXT:
          terminalreporter.write_line("[结果快照] 本次为「收集」或「零执行」，跳过写入 —— 保留既有基线")
          return
      ...
      snap["scope"] = " ".join(getattr(cfg.invocation_params, "args", ()) or ()) or "(默认全量)"
  ```
- ★ **加 `scope` 字段很关键**：快照天然只能反映"最后一次执行"。带上命令行范围后，
  一眼能看出这份快照是"全量"还是"单条复跑"，避免把子集样本当基线引用。
- ★ **通用水位**：「会生成证据文件」的工具，都要问一句 —— **"我这个命令会不会把它冲掉？"**
  验证方式：改完后**故意跑一次收集/空执行**，确认文件时间戳与内容都没变。
- ★ **反面同样成立**：这份快照的"脆弱"恰好说明 —— **没跑过，就没有证据**。
  交给别人的执行产物，必须是"真的跑出来"的那一次，且要有独立归档兜底。

### 14) ★★ 写库批次两条硬纪律：**失败只单条重跑** + **跑完立刻另存** ★（2026-10-16）
- **① 失败只单条重跑，绝不重跑整批。**
  反面教材：10 条目批次里 `O20` 因 adb 抖动失败 → 若图省事"重跑整批来修正单条"，
  会**重复消耗**一次性资源（本例：`I20` 每跑一次吃掉一条待验收采购单明细）→ 数据越跑越空、
