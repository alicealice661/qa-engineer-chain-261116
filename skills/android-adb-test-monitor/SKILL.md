## 一、接入设备

```bash
adb connect 192.168.2.x:5555
adb devices -l
```

连不上时的排查顺序：
1. `ping` 确认主机可达（同网段通常 1ms）
2. `arp -a | grep <ip>` 拿 MAC
3. 尝试 `adb connect <ip>`（默认 5555）
4. **5555 报「目标积极拒绝」= 设备侧没开网络 adb**，需 USB 接上后 `adb tcpip 5555`，不是 IP 问题
5. 需要更大范围排查时用 Python asyncio 扫端口（bash 的 `/dev/tcp` 循环太慢）

识别设备是什么：`getprop` 拿型号/系统，截图比读文档快 —— `adb exec-out screencap -p > shot.png` 再直接看图。**开机在当前页可能只是设置页，别急着定性，配合下列命令一起判断。**

### 定位「被测应用」和「业务页面」（很实用的三招）

```bash
# 1. 列第三方包 + 安装路径
adb shell "pm list packages -3 -f"

# 2. 列出每个包的业务 Activity 类名——类名往往直接暴露业务语义
adb shell "dumpsys package <pkg> | grep -oE '<pkg>/[A-Za-z0-9_.\$]+'" | sort -u
# 例：com.ali.shcema/...activity.EnterAndExitMainActivity → 出入库主界面
#     com.ali.shcema/...view.face.FaceScanActivity    → 人脸扫描
#     .../MaterialByDocumentActivity                  → 物料选择页

# 3. 包名/类名猜不出时，看安装时间 + 版本，与上一轮报告里的版本基线对照
adb shell "dumpsys package <pkg> | grep -E 'versionName|firstInstallTime|lastUpdateTime'"
```

USB 设备也能反推硬件：`lsusb` 看厂商 ID（如 `0x4b43` = 佳博标签打印机、`222a` = ILITEK 触摸屏、`4b43:3538` 等）。
**只挂 adb 一条连接 = 业务还没起；出现到后端的长连 = 已进业务页**，可用作「用户是否开始操作」的判据。

## 二、环境关键坑（必读）

| 坑 | 现象 | 解法 |
|---|---|---|
| **adb server 被回收** | 每次独立 Bash 调用都出现 `daemon not running`，已连接设备掉线报 `device not found` | 同一命令内完成 `adb connect` + 操作；或 `adb start-server` 后 `sleep 2` |
| **daemon 重启慢** | daemon 被杀后重新拉起需 30~50s | 采集脚本必须带重连循环；验证时至少等 30s 再判断失败 |
| **`nohup ... &` 会被回收** | 前台 Bash 调用结束即被杀 | 监测必须用**托管后台任务**（run_in_background），不要 nohup |
| **中文输出乱码** | Windows 下 `ipconfig`/`arp`/`tasklist` 输出被 grep 当 binary | 管道加 `iconv -f GBK -t UTF-8` |
| **`ss` 输出带方括号** | 对端是 `[::ffff:192.168.2.171]:18011` | grep 匹配时**不能带** `]`，只 grep 端口号 |
| **无 root，fd / 串口不可观测** | `su` not found；`/proc/<pid>/fd`、`/proc/tty/driver/serial` 均 `Permission denied` | **fd 轮询方案直接作废**，别沿用老脚本；替代面见下方「串口/内核观测」 |
| **dmesg 可读但噪声极大** | 无过滤时 1 分钟 170KB，多数是自身 adb 命令触发的 avc 拒绝 | 必须「关键词白名单 + 墙钟前缀」，见下方 |
| **logcat 字段位置** | `09-14 14:44:45.145 1709 1709 W System.err: ...` | level=`$5`，tag=`$6`（`$1`日期 `$2`时间 `$3`PID `$4`TID） |
| **摄像头 FPS 刷屏** | `ExtCamDevSsn ... debugShowFPS` 每秒 1 条 | 过滤流里先 `case *debugShowFPS*|*ExtCamDevSsn*) ;;` |
| **`logcat -d \| grep` 会挂死** | daemon 抖动窗口内执行，报 `waiting for device` 后一路卡到 SIGTERM（**假象像"设备离线"，实为管道+daemon 竞争**） | **先落盘、再本地筛**：`adb logcat -d -t 8000 > recon/xx.txt` 后本地 grep（`adb -b crash` 同理）；连接与目标命令务必同一条命令内 |
| **adb server 反复自杀** | 连续多次 `daemon not running; starting now`，每轮都掉设备 | 每次调用开头 `adb start-server >/dev/null; sleep 1; adb connect <ip>:5555`，**不要依赖上次的会话** |

### 串口 / 内核观测（无 root 设备）

想监测称重串口（`/dev/ttySx`）时，按下列顺序找可用手段：

1. `su 0 id` / `id` —— **先确认有没有 root**，没有就直接放弃 fd 路线；
2. `cat /proc/tty/driver/serial` —— 有 rx/tx 计数，**最理想**（无 root 时通常 Permission denied）；
3. `cat /sys/class/tty/` —— 只列设备名，不给占用状态；
4. **`dmesg`** —— 一般 shell 可读，作为替代观测面（SELinux 拒绝 / USB / mmc / OOM / 驱动事件）；
5. **应用自身的 logcat 串口日志** —— 最高优先级，往往比内核观测更有价值：
   - 至少会打「打开/关闭」：`SerialPortHelper: /dev/ttyS8 串口已经打开`、`serial_port: Opening serial port /dev/ttyS1 with flags 0x2` / `open() fd = 85`
   - **部分应用会打原始读数**，例如 `MaterialByDocument: 串口收到 hex=0A0D203030303030 ascii=00000`（实测 **10Hz**，帧结构 `\n\r` + 符号位 + 5 位 ASCII 数字）→ **可直接做精度/漂移/稳定性离线核验**

> ⚠️ **判定「应用不打点」前必须做两件事，否则会误判**（踩过坑）：
> 1. **扩大关键词**：不要只 grep `串口/serial/ttyS`，读数打点常用**业务 tag + 中文文案**（如 `串口收到`、`重量`、`读数`）。先跑 `awk '$5=="I"{print $6}' app.log | sort | uniq -c | sort -rn` 看全部 tag 分布，再定向 grep。
> 2. **换检索窗口**：读数往往**只在进入某个业务页之后**才产生。测试前采的那段日志里当然 0 命中 —— 断言「0 命中 = 应用不打点」是把「窗口内没有」当成了「全量没有」。
>
> 正确做法：**测试结束后在完整日志上复核**，且按 tag 归类看一遍再下结论。

> 若确认真的一条都拿不到：**如实写「本轮无法从数据侧核验」，不编造**，同时向用户索取现场人工读数，并把「补关键路径日志」作为可测性建议交给开发。

### 串口读数可直接用于称重判定的三个量

拿到 `ascii=` 读数后（数值单位/分辨率需向现场确认，实测有「分辨率为 50 整数倍」的秤）：
1. **稳定平台值**：连续相同值 ≥5 次（≈0.5s）视为一次稳定称重 → 与该负载的标准值比对得精度
2. **零点漂移**：空载时读数的长期分布（含负值，实测出现 `-00400`）
3. **取放瞬间跳变**：加载/卸载事件前后的极值差 → 判断是否「移动中取瞬时值」

**dmesg 增量采集的正确写法**（否则体积爆炸）：

```bash
# 只保留白名单关键词 + 每行加墙钟前缀，便于与操作时间对齐
NEW=$(printf '%s\n' "$RAW" | awk -v last="$LAST" '{t=$0; sub(/^\[ */,"",t); sub(/\].*/,"",t); if (t+0>last+0) print}')
printf '%s\n' "$NEW" \
  | grep -iE "ttyS|uart|serial|usb|dwc3|mmc[0-9]|watchdog|oom|lowmemory|killed|died|reboot|panic|avc: denied.*app=" \
  | sed "s/^/$TS | /" >> "$DMESG"
# 白名单后仍体积过大时，再排除自身命令噪声：
#   grep -viE "healthd: battery|logd: logdr"
```
| **并发 adb 命令互相踩** | 多个 adb 命令并行发起时随机报 `device not found`，串行则完全正常 | 驱动内加**全局可重入锁**强制串行；不要并行发起 adb 调用 |
| **`logcat -c` 权限不足** | `logcat: failed to clear the 'main' log`（定制 ROM 未授予 log 权限） | **降级不中断**：记录当前总行数作基线，只分析基线之后的尾部日志 |
| **pytest 解释器选错，`--html` 直接报错** | `error: unrecognized arguments: --html=...`，或 `No module named pytest` —— 用了系统 Python（pytest 9.x，**没装 pytest-html**）或裸 `python` | 本机固定用 `~/.workbuddy/binaries/python/envs/default/Scripts/python.exe -m pytest`（pytest 8.4.2 + pytest-html + openpyxl + pillow 都在这个 env 里）；**必须 cd 到工程根目录**再执行，否则 `pytest.ini` 读不到、`--html` 等 addopts 失效 |
| **`uiautomator dump` 偶发失败** | 息屏或渲染中途 dump 报错、层级为空 | 先 `input keyevent 224` 唤醒屏幕；dump 重试 3 次 |
| **★ `uiautomator dump` 在「持续刷新」界面上【必然】失败** | 报 `ERROR: could not get idle state`，重试多少次都一样。典型：相机预览（30fps 连续出帧）、高频刷新（120ms/次）的界面 | **重试无意义，改走截图路径**：`screencap` + 图像分析（见「画面级监测」）。注意**改成 `ImageView` 静态帧显示也救不了**——只要刷新间隔够短（实测 120ms），UI 仍永远不 idle |
| **★ 设备 `adb pull` 后判断「是否拉取成功」用 stdout 会永远失败** | `subprocess` 里检查 `"1 file pulled" in r.stdout` 恒为 False（实测该字符串走 **stderr**） | 改用 **文件存在 + `os.path.getsize() > 2000`** 判定；`subprocess.run(..., text=True)` 另补 `encoding="utf-8", errors="replace"` |
| **长任务看不到中间输出** | 管道 `\| tail` 有缓冲，脚本跑完才出结果 | 用 `run_in_background` 托管，或重定向到文件后再读 |
| **管道里 grep 导致「日志变少/信号消失」** | `adb shell "logcat -v time \| grep -iE 'xxx'"` 做**限时流式监听**时，grep 在 stdout 非终端下是**块缓冲**；到点 kill 掉进程时缓冲区未刷新数据**整批丢失**。典型症状：监听 30s 得 37 行、监听 180s 只 27 行（与时长无关），且内容全是窗口最开始一瞬。极易被误判为「设备 logcat 缓冲太小」或「心跳/连接断了」 | **不要在 adb shell 管道里做过滤**：把原始流回本地，在脚本侧过滤。且必须**持续排空管道**（独立线程/进程读），否则管道写满会让设备端 logcat 阻塞。**任何"信号消失"结论，先做第二数据源交叉验证**（如全量 `logcat -d`）再下判断 |

## 三、搭三路监测（测试前）

写一个 `monitor.sh`，三路并行流 + 自动重连：

1. **全量日志**：`adb shell logcat -b main,system,crash,events -v threadtime`
2. **应用过滤流**：从全量中按关键词分流（应用包名 / 业务词 / 崩溃词），先剔除 FPS 噪声
3. **触控行为轨迹**：`adb shell getevent -lt | grep --line-buffered BTN_TOUCH`
   - 作用：拿到每次点击的 DOWN/UP 时间戳，用于「用户动作 ↔ 日志」对齐
4. **（可选）网络连接采样**：每 5s 统计一次 `ss -tn` 的目标端口连接数

分配置文件：`full_<尾号>.log` / `app_<尾号>.log` / `touch_<尾号>.log` / `net_<尾号>.log`（**多设备时按 IP 尾号区分**，避免与历史设备日志混淆）。每个开头写一行 `==== BASELINE <时间> ====` 作为基线标记。

再写一个 `peek.sh [app|full|touch|err|mark|size] [行数]` 方便随时拉数据。

启动方式：`run_in_background=true` 跑 `bash monitor.sh`，**等 30s 以上**再验证文件是否在长。

### 建议加满 5+2 路（实测最有价值的组合）

| 流 | 命令 / 方法 | 作用 |
|---|---|---|
| 全量日志 | `logcat -b main,system,crash,events -v threadtime` | 兜底，一切争议的最终证据 |
| 应用过滤流 | 全量中按关键词分流 | 快速定位 |
| 触控轨迹 | `getevent -lt` 抓 `BTN_TOUCH` + **`ABS_MT_POSITION_X/Y`** | 带坐标才能还原「点了哪儿」 |
| 网络连接 | `ss -tn` 每 5s，**排除 `:5555` 后**统计业务连接 | 连泄漏 / 后端断连 |
| **前台 Activity 变化** | `dumpsys window \| grep -a mCurrentFocus \| tail -1`，**只在变化时记录** | 页面轨迹还原，性价比最高的一条 |
| **内存采样** | `dumpsys meminfo`（系统 RAM + 关键应用 RSS）每 60s | 泄漏趋势 |
| **专用 crash buffer** | `logcat -b crash -v threadtime`（**不加关键词过滤**） | 崩溃堆栈专用，永不被刷掉 |

> ⚠️ **`grep -m1 mCurrentFocus` 是陷阱（2026-09-23 实测踩坑）**：`dumpsys window` 输出的**首行 `mCurrentFocus` 恒为 `null`**，真实前台窗口在**第二行**。用 `-m1` 会让页面变化**永远检测不到**——曾导致 180 秒轮询全程误报"无变化"，恰好漏掉用户真实操作。
> **正确写法**：`dumpsys window | grep -a mCurrentFocus | tail -1` 或 `dumpsys activity activities | grep -a ResumedActivity`。轮询脚本务必先用"手动切一次页"自验能测到变化，再投入使用。

> 触控/网络/UI/内存流的实现细节：见工作区 `monitor59.sh`、`extra59.sh` 可直接复制改造。

### ★ 画面级监测：颜色掩膜自动判别「画面上画出来的东西」

适用场景：**界面持续刷新导致 `uiautomator dump` 完全不可用**，但仍需量化记录界面状态 ——
例如目标检测框（数量/位置/类别颜色）、状态指示灯、告警色块。此法已在掌部识别 APK 上 74 帧实测验证。

思路：**已知配色 → 逐通道查表求掩膜 → 计数 + 求包围盒**，全程纯 PIL（C 速度）。

```python
from PIL import Image, ImageChops
# 预生成查表（一次），TOL 取 26 左右
lut = [255 if abs(v - R) < TOL else 0 for v in range(256)]
r_ch, g_ch, b_ch = im.convert("RGB").split()
m = ImageChops.multiply(ImageChops.multiply(r_ch.point(lut_r),
                                            g_ch.point(lut_g)),
                        b_ch.point(lut_b))
cnt  = m.histogram()[255]     # 该颜色的像素数（超过阈值即认为存在）
bbox = m.getbbox()            # 该颜色的包围盒（判断位置：居中 / 贴边 / 落在空白区）
```

关键经验：
- **该机 Python 3.12 没有 numpy**（`ModuleNotFoundError: No module named 'numpy'`）。
  不要写 `import numpy`，用上面的 PIL 查表法。
- **必须限定分析区域**：截图含右侧信息面板，面板里的同色文字/色条会被误计。
  先量出预览区宽度，只分析该区域（例：`im.crop((0, 0, 1500, h))`）。
- 掩膜 `histogram()[255]` 计数用于「有/无」判定；`getbbox()` 用于「落在哪」判定 ——
  **两者结合才能区分"正常检出"与"高置信度误报在空白区域"**。
- 抓帧用 `screencap -p /sdcard/x.png` + `pull`（不要用 `exec-out` 重定向，
  Windows/Git Bash 下会做换行转换破坏 PNG）。
- 用 **STOP 文件**做优雅退出（脚本每轮检查），比 kill 进程干净。
- 帧归档只保留最近 N 帧（脚本内按期号清理），否则长时间监测会撑爆磁盘。
- **局限**：读不出界面文字。需要具体数值时，对存下的帧做 `crop` + 放大 + 增强后人工读（见下节）。

### ★ 从存下的帧还原「屏幕上的分数/数值」并出对照证据图

颜色掩膜只能告诉你「框是什么颜色」，**拿不到具体分数**。监测脚本若只记了主色，用下面的做法补齐成「有分数」——实测从 640×480 抓帧里清楚读出了 `band=0.0724 nail=0.0004 ring=0.4199 unknown=0.0533 yes=0.4541`。

```python
from PIL import Image, ImageEnhance
im = Image.open(frame).convert('RGB')
c = im.crop((640, 590, 1360, 670))                     # ① 先粗裁定位数值条（屏幕下方）
c = c.resize((c.width*4, c.height*4), Image.LANCZOS)   # ② 放大 ×3~×5
c = ImageEnhance.Contrast(c).enhance(1.5)              # ③ 提对比
c = ImageEnhance.Sharpness(c).enhance(2.0)             # ④ 锐化
c.save(out)
```

- **数值条/状态条的位置要先用 PIL 量**，别按阅读器显示的坐标猜：逐行统计某段 x 范围的平均亮度，**黑底条的亮度会明显塌陷**（实测 y 534–566 处 154 → 52），据此定 y 区间。
- 局部细节（指甲、戒指、异物形状）同样可辨：`crop + resize(LANCZOS, ×3~×9) + Contrast 1.35 + Sharpness 1.8~1.9`。
- **拼「对照证据图」最能说服供应商/开发**：把两帧同区域裁图纵向拼接，每格上方用 `C:/Windows/Fonts/msyh.ttc`（正文）/ `msyhbd.ttc`（标题）写一行结论 + 一行数据，比例不同的图先等比缩放居中到统一画布再贴。
- **★ 同一对象必须跨帧交叉验证**：同一个物理目标（戒指/创口贴/指甲）在相邻帧里的分数可能天差地别（实测同一枚戒指 3 秒内 `0.0042 → 0.9863`，235 倍）。**单看一帧会把它判成「识别正确」或「完全失效」，都是错的。** 给任何关键帧定名前，先扫 ±5 帧同区域对照。
- **★ 命名即结论**：证据文件名要带判定（`01_美甲手_判正常_漏判nail_yes0.917.png`），不要用中性名（`01_裸手平放_判正常.png`）。中性名会在后续引用时把错误结论带出去。
- **现场 ground truth 优先**：手上戴没戴戒指/美甲、物体怎么摆的，**问人比看图可靠**。图像推断只用于确认，不用于定性。

```bash
grep -iE "FATAL EXCEPTION|ANR in|tombstone|SIGSEGV|beginning of crash" full.log

# 2. 日志规模与级别分布
awk 'NF>=6{print $5}' app.log | sort | uniq -c | sort -rn
```

### ★ 真人操作型功能流程：截图序列 + 双源采集（实测最优范式）

**场景**：功能流程必须**真人配合**（刷脸、放手、答题），无法脚本驱动，且窗口只有几十秒。

**采集命令（主方案：录屏；`run_in_background=true` 跑，全程不清 logcat）**：

```bash
D="-s <ip>:5555"
adb $D shell "svc power stayon true"                      # 防熄屏录到黑屏
adb $D logcat -v threadtime > recon/live_logcat.txt 2>&1 & LP=$!
adb $D shell "/system/bin/screenrecord --bit-rate 12000000 --time-limit 90 /sdcard/rec.mp4"
kill $LP; adb $D pull /sdcard/rec.mp4 recon/
# 之后 cv2.VideoCapture 抽帧：step = round(fps / sample_fps)，2 fps 足够判页面推进
```

**★ 采集方式性能：必须录屏，不要逐帧 screencap（2026-09-24 实测，会直接导致漏测）**

| 方式 | 实测速率 | 评价 |
|---|---|---|
| 逐帧 `screencap`（含设备端循环下发） | **0.25 fps** | ❌ 必然漏掉耗时短的步骤 |
| `/system/bin/screenrecord` 录屏 | **54 fps**（1920×1080） | ✅ 主方案，零漏采，可任意抽帧 |

- **瓶颈不在 adb 往返**：设备端本地 `screencap` 仅 **172ms/帧**；真因是**亮屏彩色页 PNG 编码**——帧体积 1.88MB，编码约 **4s/帧**。曾误判为 adb 往返慢，改用「设备端循环一次性下发」，20s 仍只采到 20 帧。
- **实际教训**：以 **2 秒间隔**截图，**漏掉了「第 1 步进行中」状态**，复盘时误以为流程"跳过了这一步"。起初归因为**采样率不足**，后经**逐帧扫描推翻**——真因是**判据阈值把该阶段整段滤掉**（见 §七「全自绘页面」的三步归因法）。**归因前务必逐帧扫描坐实。**
- 录屏 `pull` 后**抽帧**再分析：既得到细粒度时序，又能按需保留关键帧，文件还远小于 50 张 PNG（8s 录屏约 7.5MB vs 50 帧约 83MB）。
- 逐帧截图仅保留用于**取原始 PNG 关键帧**（降级用途）。
- **`pull` 下来的 mp4 要给 cv2 分析时，路径不能含中文**（`cv2.VideoCapture` 不支持非 ASCII）→ 先 pull 到系统临时 ASCII 路径分析，再把文件拷回工作目录留存。

要点：
- 帧存**设备端**目录，结束后整目录 `pull`。
- 单帧 png 约 1.8MB（1920×1080 彩色页）。
- **先按文件大小排序**即可粗判页面类型：不同页面字节数明显不同（**明显异动处就是页面切换点**），比逐帧打开快得多。
- 用 `logcat` 的 `START u0{...} from uid ...` / `Displayed` 精确定位流程起止与跳转链，与帧号对齐。

**★ 双源采集（缺一不可，任一缺失不得径直判「未走通」）**：

| 源 | 取法 | 负责证明 |
|---|---|---|
| ① 界面证据 | 上述截图序列 + `logcat` Activity 跳转 | **流程路径**（走过哪些步、顺序） |
| ② 落盘数据 | `shared_prefs` 结果字段、业务侧产物目录（抓拍/导出文件） | **结果正确性**（业务值对不对） |

实测案例：界面证据全部丢失的情况下，靠「业务抓拍目录（**文件名 = 毫秒时间戳**，每次流程固定 3 张，环节可从画面辨认）+ `shared_prefs` 结果字段」**完整还原了一次完整流程**，证据强度不低于截图。

其他可用的落盘断言源：
- **`shared_prefs/<pkg>_preferences.xml`**：`run-as <pkg> cat shared_prefs/*.xml`（应用可 debug 时直读，**明文 JSON/XML 常见**）→ 配置类断言的最优源。
- **业务产物目录**：形如 `/sdcard/<业务名>/<毫秒时间戳>.<ext>`，**文件名即时刻**，可直接反推事件时间线。
- **流程前后各存一份配置**，`diff` 出**本次流程新增/变更的字段** —— 比凭空列出全部字段高效得多。

**★ 采集脚本必先自验**：轮询/监测脚本启用前，**手动切一次页面确认能测到变化**再投入使用。否则会像下面这样静默失效：
`dumpsys window | grep -m1 mCurrentFocus` 首行恒为 `null` → 监测全程误报"无变化"（详见第三章表格下方警告）。

### 无法直连抓日志时：从实拍照片还原屏幕日志

对方（供应商 / 现场同事）只发来**拍屏幕的照片**时，照片上的日志区可以直接还原出原始分数与报错——**不要因为"拿不到 logcat"就放弃取证**。

```python
from PIL import Image, ImageOps, ImageEnhance
im = Image.open(src).crop((0, y1, W, y2)).convert('L')   # 先粗裁定位日志区
w, h = im.size
im = im.resize((1568, int(h * 1568 / w)), Image.LANCZOS)  # 放大到 1568 宽
im = ImageOps.autocontrast(im, cutoff=1)
im = ImageEnhance.Sharpness(im).enhance(2.0)
im.save(out)
```

要点：
- **放大到 1568 宽**是可读性上限，再宽会被压缩反而更难认
- 先粗裁读一次确认位置，再精裁；**日志区通常在画面下方 60%~80% 高度**，位置猜错就重裁，别硬猜内容
- 必须转灰度 + `autocontrast` + 锐化，对屏幕反光与摩尔纹效果明显
- 照片里的日志是**滚动快照**，很可能不是当前帧——读数要与界面上的框/文字交叉确认；两者打架时以能确定的那一帧为准
- 还原出的分数再与 `adb logcat -d` 历史缓冲对一次；缓冲区已滚掉就安排下一轮主动复现

### 附件抢救（微信 / IM 临时目录）

从微信收到的文件位于 `...\RWTemp\...`，**会被自动清理**，收到即归档，不要就地分析：

```bash
cp "<RWTemp路径>/xxx" "<目标目录>/"
md5sum "<源>" "<目标>"        # 校验一致再删源
```

本工作流已多次遇到「关键材料只存在于临时目录」，且用户桌面也发生过被清理的情况 —— **先复制、再分析、留 MD5**。

### 交叉编译 native 程序（NDK + CMake）

设备的 native 程序（算法 SDK demo、探针、二开验证）必须在主机侧交叉编译再推到设备跑。

```bash
# 1. 工具链：pip 装 cmake/ninja（各几十 MB），不必下大安装包
<python-env>/Scripts/pip.exe install cmake ninja

# 2. NDK（约 445 MB zip，下载约 6 分钟，解压后 2 GB+）
curl -L -o ndk.zip https://dl.google.com/android/repository/android-ndk-r25c-windows.zip
unzip -q ndk.zip -d /d/ndk

# 3. 配置 + 编译
export PATH="<python-env>/Scripts:$PATH"
cmake -G Ninja \
  -DCMAKE_TOOLCHAIN_FILE=D:/ndk/android-ndk-r25c/build/cmake/android.toolchain.cmake \
  -DCMAKE_BUILD_TYPE=Release -DANDROID_STL=c++_static \
  -DANDROID_PLATFORM=android-24 -DANDROID_ABI=arm64-v8a \
  -DANDROID_TOOLCHAIN=clang -DANDROID_ARM_NEON=1 ..
ninja -j4
```

要点：
- ⚠️ **`-fuse-ld=gold` 在 NDK r23+ 已不可用**（GNU gold linker 被移除）。老工程里常见这个写法，**编译失败第一嫌疑就是它**，改成 `-fuse-ld=lld` 即可。
- 验证产物架构：ELF 的 `e_machine == 0xb7` 才是 AARCH64；`file` 命令在 Windows 上可能不可用，用 Python 读 ELF 头更稳。
- 运行时依赖的 `.so` **优先在工程包内 thirdparty 目录找**，避免从设备回捞；设备侧用 `LD_LIBRARY_PATH=.` 就地加载。
- `ANDROID_PLATFORM` 取低值（如 `android-24`）兼容性更好。
- 未定义宏若出现在**函数声明位置**，预处理器不展开、编译器当普通声明处理，**不阻塞编译**——不要看到未定义宏就判定编译失败，实际编一次为准。
- 产物可能很大（静态链接 OpenCV 等可达 40 MB+），推送前先确认体积与设备剩余空间。

### 高价值判据（经验）

- **连接数单调只增不减** → 连接泄漏的强判据。配合「Activity 栈深度」与「Native Heap 大小」三者互证，可判定为**系统性资源管理缺陷**而非偶发。
- **Activity 回退栈里同一 Activity 出现多个实例** + `Activities`/`ViewRootImpl` 计数超标 → 页面未 `finish()` 导致栈泄漏，其持有的 View/硬件资源/连接会一并滞留。
- **Native Heap 远大于 Dalvik Heap** → 泄漏在 native 层（摄像头 buffer / 算法 SDK / JNI 全局引用），不是 Java 层内存问题。
- **★ 算法类设备（识别/检测）专属判据**——评测"算法准不准"时，四条比"准确率"更有杀伤力：
  1. **双向失效**：不只统计漏判，**误报和漏判要同时给**。实测掌部识别 `ring` 类真戒指召回 1/3、无戒指误报 2/2 —— 单向看都发现不了。
  2. **输出不可复现**：同一物理目标在相邻帧分数跳变（实测 3 秒内 0.0042 ↔ 0.9863）。**这是最硬的一条**，因为现场"同一动作重做得到相反结论"无法用"样本不足"解释。建议补做「同一张图重复推理 N 次」验证确定性。
  3. **响应的是低层特征而非语义**：改变物体的**摆放方向**就跨类（实测同一创口贴竖放→"戒指"0.98、横放→"绷带"0.94）。说明模型学的是形状/朝向，不是"这是不是戒指"。
  4. **兜底类吞信号**：`unknown` 在无异物时也占 0.90~0.99，真实异常只在 1e-3 量级 → 信息量被兜底类吃掉。
  > 统计口径：不要只报"准确率"，要报**每类的召回 / 误报（各自分母）+ 分数分布区间 + 同帧一致性**。

### 业务数据真伪校验（营养/计量类终端）

**Atwater 系数自洽性校验**：`碳水×4 + 脂肪×9 + 蛋白×4`（kcal）→ `×4.184` 得千焦，与显示热量比对。
- 自洽（误差 <1%）→ 数据可信，客户端无换算错误
- 不自洽 → 先查**后端下发原文**（grep 接口 JSON），若后端就是脏值则是录入问题，**不计入客户端缺陷**
- 另需查逻辑约束，如「膳食纤维 ≤ 碳水化合物」

### 计量精度判定（称重类终端）

**优先走数据侧**：先按「串口 / 内核观测」一节的第 5 步确认应用是否打了串口原始读数。**若能拿到读数，精度判定就用日志做**（稳定平台值 / 零点漂移 / 取放跳变），不必依赖人工目视 —— 这一步能省掉整个「靠现场读数补数据」的往返。

**只能人工读数时**，用标准砝码测同一重量，**先看偏差方向，再看幅度**：

| 观测特征 | 结论指向 | 处置 |
|---|---|---|
| 偏差**单向且恒定**（如恒低 3%） | 零点漂移 / 标定系数错误 | 零点校准 + 标准砝码标定 |
| 偏差**双向**（同一砝码有时偏高有时偏低） | **排除单纯标定问题**；多半是**读数取值时机**（移动中取瞬时值）或**滤波不足** | 先做「静置 vs 取放瞬间」对照实验 |
| 偏差呈整千/整百倍（如 1kg→1克） | 单位换算 bug | 查单位转换代码 |

**「静置 vs 取放」对照实验（成本最低、结论最硬）**：
1. 砝码静置不动连续观察 30s —— 仍跳变 ⇒ 硬件/滤波问题
2. 静置读一次、取走瞬间读一次 —— 仅取放瞬间跳 ⇒ 取值时机问题

**多档标定**：500g / 1kg / 5kg 各测 3 次，单点不足以定性；误差随量程线性放大 = 系数问题，各档同幅偏差 = 零点问题。

**迭代复测时注意**：上一版若只给了「≤100g」这类单点乐观结论，本版要把区间和样本量一并核对 —— 新观测落在旧区间内不等于「未恶化」，可能只是旧版样本太少。

- **稳定性结论要分维度**：别只写「无崩溃」就下结论，崩溃 / 内存 / Activity / 连接 要分开说

```
SerialPort raw=<原始报文> parsed=<解析值>g net=<净重>g display=<屏显>g
```

一行日志即可让后续每轮复测从「人工目视」升级为「数据核验」。

## 七、设备端 UI 自动化测试工程（可重复回归）

当同一设备需要**多轮重复回归**时，把上述手工流程升级为可复跑的 pytest 工程。已在 RK3568 / Android 11 晨检仪上跑通（用例清单 36 条 / 已实现 32 条 / 35 个执行项，全量约 14 分钟）。

### 技术选型：原生 adb + uiautomator dump

**不要**用需要推送端上 agent 的方案（uiautomator2 / Airtest 的 agent 模式）——内网隔离环境推不上去。原生 `uiautomator dump` 零依赖、可离线，是内网设备的首选。

```bash
adb shell uiautomator dump /sdcard/ui.xml; adb shell cat /sdcard/ui.xml   # 拿层级
adb exec-out screencap -p > shot.png                                      # 拿截图（exec-out 不做换行转换）
```

工程分层（铁律：用例层不出现裸 adb，驱动层不含业务断言）：

```
framework/  adb_driver.py(连接/锁/dump/截图/日志) + ui_node.py(XML→节点对象)
pages/      PageObject（元素与操作语义化）
tests/      conftest.py(设备fixture) + test_*.py(只写业务断言)
```

### ★ 全自绘页面（`uiautomator dump` 空壳）怎么断言：几何 + 颜色签名

**症状**：`uiautomator dump` 只返回一层空壳（如单个 `FrameLayout`），**无 `resource-id`、无可点控件** → 定位器五级自愈全部失效，常规 UI 自动化无从下手。这类页面是**整屏自绘**（Canvas / SurfaceView），常见于一体机、排队机、体检/晨检类终端。

**解法：不找 id，从"人眼能看见的稳定视觉结构"里造隐形 id。**

优先级排序：

| 判据 | 稳定性 | 说明 |
|---|---|---|
| **几何量**（位置 / 高度 / 长度） | ★★★ | 进度条高度、指示条长度、卡片位置——与文案无关 |
| **颜色签名**（HSV 掩膜占比） | ★★★ | 状态图标的颜色 + 内部图案面积占比 |
| **模板匹配**（关键文案） | ★★ | 同状态 1.000、异状态常 ≤0.85，阈值取 0.95 |
| 绝对坐标点击 | ★ | 仅用于触发，不作为断言 |

**四步落地法**：
1. **从实测帧标定坐标**：取“该结构最清楚”的一帧，用颜色掩膜 + `connectedComponents` 求出连通域的 `box` 与 `center`，**不要靠肉眼看图估坐标**。
2. **统计各状态的颜色签名**：对每个图标开一个固定尺寸采样窗（如 30×30），算 `颜色掩膜占比 / 近白占比`。**先采集真实数据再定阈值**——本次实测三种状态天然分离（见下表），无需调参。
3. **定阈值 + 过滤规则**：非目标页面常有同色元素（实测主页有绿色元素，绿域仅 17px 高）→ 必须加**长度/面积下限**过滤，否则误判。
4. **写 `selftest`**：把标定结果做成断言自测命令，**判据一旦漂移立刻暴露**（改分辨率/换版本/改 UI 后第一时间跑）。

**实测案例（RK3568 晨检仪，单页五步状态机，1920×1080）**：

| 判据 | 标定值 |
|---|---|
| 步骤图标 | `x=1295`；第 i 步 `y = 227 + 175×(i-1)`；采样窗 30×30 |
| 进度绿线 | x 1260–1330；起点 `y=204`；终点 = 当前步 y + 87 |
| **颜色签名** | **已完成 `0.75/0.24`**（绿/白）｜**进行中 `0.47/0.50`**｜**待办 `0.00/1.00`** |
| 非流程帧过滤 | `绿线高度 ≥ 100`（**2026-09-24 由 250 下调**；主页干扰项仅 17px，而"第 1 步过渡态"绿线仅 **175** —— 阈值取 250 会把**整个第 1 步阶段滤掉**） |

- **当前步推导**：`(绿线终点 - 87 - 起点) / 步间距`，四舍五入。
- **单调性校验**：流程类进度**只许前进**；但**同一次录屏可能含多轮流程**（用户连走两趟），此时**「高步 → 低步」是新一轮开始，不是回退缺陷**——只有"第 1 步以内回退"才判异常。（2026-09-24 踩坑：未区分多轮，误报 NG）
- **配套**：标定常量单独放配置文件（如 `conf/e2e_progress.json`），脚本读配置，改 UI 只改配置不改代码。

> **优势**：不依赖 OCR、不依赖控件、不依赖网络，纯本地图像计算，**一帧判定耗时 <50ms**，可实时跑。

### ★ 自绘页要「点得动」：模板匹配动态求坐标 + `input tap`（**禁硬编码坐标**）

**常见误区（2026-09-24 踩坑）**：把「**判步 / 断言**」当成「**控件定位**」交付 —— 判步回答"走到第几步"，定位回答"某个**可点控件**在哪"。二者**不可互相替代**；自动化链路要能闭环，必须两者都有。只做判步就宣布"UI 定位已落地"，是**偷换目标**。

**硬性要求**：`adb input tap` 的坐标**必须由 `cv2.matchTemplate` 动态求得，禁止手工硬编码**。硬编码坐标在换分辨率 / 换版本 / 换背景后**静默失效**（点空），**不报错**，极难发现。

**落地骨架（6 子命令）**：

| 子命令 | 作用 | 关键点 |
|---|---|---|
| `crop` | 从基准图裁控件模板（建档） | **唯一一次需要人工给位置**；此后不再出现人工坐标 |
| `locate` | 单图定位 → `{hit, score, center, box}` | `center` 全部来自匹配峰值；配置里的 `roi` 只是**搜索范围**，不是坐标 |
| `tap` | 实时截图 → 定位 → `input tap` | **定位不达门限即拒绝点击**（防误点）；保留 `--dry-run` 只算不点 |
| `selftest` | 跨帧回归：期望命中 / 期望不误报 | 判据漂移**立刻暴露** |
| `sweep` | 扫整目录统计命中分布 | 查**误报面** —— 不含该控件的页面一律不得命中 |

**三条实证结论（RK3568 晨检仪 1920×1080，主页「开始晨检」按钮）**：

1. **定位精度远高于门限敏感度**：跨 3 天、**背景插图整体更换**（两张完全不同的厨房插画）的 4 张主页图，命中坐标**全部落在 (1547,673±2)** —— **零漂移**。说明特征来自控件本身，不是背景巧合。
2. **门限必须由实测分布确定，不能拍脑袋**：该按钮有**明暗两态周期闪烁**（呼吸动画）—— 暗态 NCC **0.6118**、亮态 0.94。若按经验取 0.8，**暗态帧整段漏检**，且同样**不报错**（只表现为"偶尔点不中"）。实测后门限取 **0.60**。
   → **这与"禁硬编码坐标"同源：阈值也是会静默失效的硬编码。**
3. **误报面必须单独扫**：整场 200 帧（主页 + 完整五步流程）命中 121 帧（60.5%），**逐张抽查确认为真主页**（人脸取景页 0.34、不命中）→ **"命中率高"本身不等于误报**，但**必须抽查**才能下结论。

**工程坑**：`cv2.imread / imwrite / VideoCapture` **均不支持非 ASCII 路径**（中文目录直接返回 None）→ 一律 `np.fromfile + cv2.imdecode` / `cv2.imencode(...)[1].tofile()`。

**配套档案**：控件清单放外部配置（模板路径 + `roi` + 门限 + `regression` 用例），**脚本内不含任何坐标**；换 UI 只改档案。

### ★ 「某步骤没采到」三步归因法（禁止直接甩给采样率）

自绘页断言里，"某步骤看不到"有三种**完全不同**的原因，误判会浪费大量时间。**必须按序排查**：

| 序 | 假设 | 怎么验 | 本次实例（RK3568 晨检仪） |
|---|---|---|---|
| 1 | **界面不存在，或换了呈现位置** | 对**原始录屏逐帧扫描**（不抽帧）看该状态是否出现过——**但别只扫你预期的那个控件，要扫全屏** | 以为"第 5 步完成页没采到"，逐帧扫 3000 帧发现进度条第 5 步**从未渲染**（点「完成」直接跳主页，相邻两帧切换 <33ms）→ 一度判"产品无此界面"。**后经用户提示复核主页**，发现界面证据**转移到了主页底部提示条**（轮播「晨检提交成功」，区域 `x893–1027/y938–978`）→ 结论修正为「**进度条无此态，但界面证据存在，只是换了位置**」，判据 = 提示条（**窗口判定 ≥6s**，单条 ~2s / 空档 ~0.85s）+ 数据层三源 |
| 2 | **被判据阈值滤掉** | 打印该状态**真实的几何量 / 签名值**，比对标定阈值 | 第 1 步绿线实测 `h=175`，低于阈值 `250` → 整段当噪声过滤。**下调阈值 + 回归自测即可修复** |
| 3 | **确实漏采** | 才是采样率 / 采集方式问题（改用录屏） | — |

**配套**：写一个"全视频逐帧扫描"命令——**只处理判据所在条带**（如 `x 1240..1350`），避免全帧解码拖慢（3000 帧可秒级完成），输出各状态段的**起止帧 + 几何量**。这是区分上述三种原因的唯一可靠手段。

> **方法论要点**：**"没采到" ≠ "不存在" ≠ "漏采"**。先逐帧扫描看"有没有出现过"，再看"是不是被自己的阈值滤了"，最后才怀疑采集方式。
> **⚠️ 两条实战教训（来自同一次踩坑，2026-09-24 晨检仪）**：
> ① **"预期控件没出现" ≠ "界面证据不存在"** —— 断言"产品无此界面"之前，必须**扫全屏**确认同一语义没在别处呈现（**底部提示条 / Toast / 角标 / 状态栏**）。本次因只盯右侧进度条，漏看主页底部提示条，把"界面证据存在"误判成"仅数据层可判"，还写进了规范，后被用户一句话点破才翻案。
> ② **瞬时 / 轮播类提示禁止单帧判定** —— 提示条类 UI 常见「**显示 ~2s ＋ 空档 ~0.85s**」轮播，单帧采样可能正好落在空档 → 必须**按时间窗口**判定（窗口 ≥ 一个完整轮播周期）；判据顺序固定：**先白占比门限、后 NCC**（整页白底页会让目标区域白占比 = `1.000`，不加 `white_max` 必误报）。

### ★ 取证铁律：「文件不在」≠「没保存」（2026-09-24 晨检仪 C-01 教训，**已反编译坐实根因**）

**踩坑**：判断"某环节是否落盘"，只对比采集前后的目录文件列表——看到目标文件不在，就判"没落盘/未保存"。

**真相**：设备端常有 **「读旧路径 → 写新路径 → 删旧文件」** 的覆盖机制，**旧文件会被后续操作主动删掉**。
本次反编译（`V10.11.002`）实测两个写盘函数**逻辑同构**：

```java
// HandPhotoSaver.saveSync() / HandPhotoWriter.writeSync()
String old = (String) spf.getParem(key, "");   // ① 读 prefs 里的「上一张」
spf.setParem(key, now);                        // ② 写回新路径
HLog.i("…", "保存照片成功: " + now);
deleteOldFile(old);                            // ③ 删除上一张
```

→ **每个 prefs key 恒留 1 张**（人脸 1 + 手心 1 + 手背 1 = **最多 3 张**）；
**新一轮流程必覆盖上一轮**（prefs 持久化 → **跨会话也覆盖**）。
被误判为"没落盘"的那一趟，日志里明明有 `保存照片成功`——**写过，只是被后面覆盖删掉了**。

**正确做法（四线并看）**：

| 线 | 取什么 | 作用 |
|---|---|---|
| ① **写入日志** | `保存…成功` 类打点 | 证明**写过** |
| ② **删除/清理日志** | `删除…` 类打点 | 证明**被清掉** |
| ③ **磁盘终态** | 目录列表 | 只反映**净结果** |
| ④ **跨会话复核** | 同操作跑 2–3 次比对日志 | 区分"偶发漏采"与"稳定机制" |

> **只看 ③**，会把「保存后被覆盖」误判成「从未保存」。
> **只看一次会话**，会把「稳定机制」误判成「本次采集异常」。

**★ 打点不对称：成功不打点 ≠ 没发生**
本次两类删除打点**不一致**——`HandPhotoSaver.deleteOldFile()` 打「删除老照片」，而
`HandPhotoWriter.deleteOldFile()` **仅在失败/异常时打点**（无成功日志）→ 日志上呈"手部照只增不减"的**假象**。
> **铁律**：某动作"日志里没看到"时，先查**是否只打了失败分支**，再断言"没发生"。

**配套排查**：① `grep -aE "保存|删除|save|delete|Saver|Writer"` 拉全**文件生命周期日志**；
② **反编译 `saveSync/writeSync` 一级写盘函数**，看有无"存新删旧"；③ **最后**才下"未落盘"结论。

**同类风险点**：日志轮转（logcat 环形缓冲）、数据库只存最新一条、缓存目录定期清理、**prefs 槽位覆盖**。

### ★ 「日志里没有」≠「没有数据」：用反编译确认请求体字段（2026-09-24 晨检仪第 4 步）

某界面步骤在设备日志里**完全静默**（窗口 8.5s 零日志、零接口调用、prefs 也无痕迹）时，**别急着下「这步没有数据源」的结论** —— 很可能产品**压根没把这个数据上报**。判定要拆两层：

1. **日志层**：该时间窗内应用进程（**按 PID 过滤**，先确认应用 PID 与统一 tag）有没有打点？有没有接口调用？（`Request Succeeded:…, :模块/接口` 时间轴最容易看）
2. **代码层**：反编译确认「这个值到底进没进请求体」——
   - 找该值的**存储位置**（内存字段 ／ prefs ／ 静态）
   - 找**提交方法**（如 `submitXxx()`），看它**读了哪些字段**
   - 找**请求 DTO 的字段全表**，确认有没有对应字段

实测：第 4 步「今日状态」的选择只存在内存字段 `healthCurrentStatus`，提交方法**只读症状列表、不读状态**，DTO **14 个字段（13 个业务字段）里没有任何 status** → **该状态不上报**（选「离岗休息」但不勾症状时，请求与「正常上岗」**完全一致**）。这是**产品设计**，**不是采集问题**。

> **判据**：若能在代码层证明「值没进请求体」，就**不要再**去日志/后端找了 —— 直接转成**改进建议**（补字段 ／ 补请求体日志 ／ 确认业务语义）。

**androguard 4.x API 坑（本次白跑两轮）**：

| 你以为 | 实际 |
|---|---|
| `dex.get_methods()` 给方法定义 | 给 **`MethodIdItem`（引用）**，**没有 `get_code()`** → 须 `dex.get_classes() → class.get_methods()` 拿 **`EncodedMethod`** |
| `dex.get_strings()` 给对象 | 给 **`str` 列表**（不能 `.get()`） |
| `apk.get_all_dex()` 可 `len()` | 返回**生成器** |

> **操作要点**：批量遍历前**先用一个样本方法验证 `get_code()` 可用**；否则异常被 `except Exception: continue` 吞掉，会**静默输出「未找到引用」**，让人误判成「代码里没有」。
> 另：字符串常量匹配用**子串**（日志文案常带冒号等后缀，全等匹配会 0 命中）。

### ★ 端点「名字像」≠「用途就是那个」：看调用方 + 响应分支（2026-09-24 晨检仪第 4 步二次取证）

当**代码证据说"设备不上报"**、而**用户/后端说"后端确实有这条记录"**时，两边都别急着让步 —— 用三步把通路彻底盘清，通常结论是**两说并存**（来源在设备之外）。

**① 全包接口清单盘查**（比只看「接口时间轴」多一层）
扫描 APK 全部端点形态字符串（`^[a-z]+(/[a-z]+)+$`），再对每个端点找它的**响应处理分支**（如 `if (url.equals("a/b")) {...}`）——那才是真实用途；最后与运行期 `Request Succeeded:…, :模块/接口` 时间轴交叉，区分「存在」与「真被调用」。

> 真实案例：`morningCheckDevice/updateCanteenEmployerInfo` 名字像「更新员工信息（含上岗状态）」，但 —
> **响应分支**是 `showToast("人脸补录成功")` + `resetFromPhoneVerify()`；
> **调用方**是 `doPhoneVerifyUpload()`，载荷 `FaceGatherDto{id, eigenvalue, pictureBase64, sign}`；
> **运行期**两轮**零调用**。→ 它是**人脸补录**，与晨检状态无关。**光看接口名会得出完全相反的结论。**

**② 写入点全表**（判定「上报／下发／纯本地」的最快一刀）
把该字段的**全部** `iput-object`／`sput-object` 引用点列出来：
- 只有「用户点击」+「初始化」写 → **既不上传也不下发**，是**纯本地 UI 门闸**（本次实测正是如此：`healthCurrentStatus` 仅 2 个写入点，**无任何响应处理回填**）
- 有响应处理写 → 该值是**后端下发**
- 提交路径读它 → 该值**会上报**

**③ 排除「分析的包不是线上包」**
`adb shell pm path <pkg>` → `adb shell ls -l <apk路径>` 取**字节数**，与本地待分析 APK 比对（能取哈希更好）。**versionName 相同不代表二进制相同**，re 前必须核。

**④ 别忘继承**：`class.get_fields()` 只给**本类声明**的字段；fastjson 按 **getter** 序列化 → **必须查父类链**，否则漏字段会直接推翻结论。

> **结论落点**：设备侧证据闭环 + 用户观察为真 ⇒ 表述为「**后端确有记录，但来源在设备之外**（管理端／其他端）」，并给一条**可判定实验**让双方都能验证：**选一个与后端当前值不同的值走完整流程，回后端比对该值是否变化** —— 变了说明还有未找到的通路（此时要用户给**字段名/页面**反查代码），不变则坐实不上报。这比争论谁对有用得多。

### 设备侧计数 / 取列表：用 `adb exec-out`（2026-09-24 踩坑）

`adb shell ls | wc -l` 在 **Windows + Git Bash** 下**计数严重失真**——同一目录实测返回 **147**、真值 **35**（约 **4 倍**偏差）。
原因：`adb shell` 的 **PTY 输出会做换行转换**，本地 `wc -l` 统计被放大。

- **凡计数、批量取列表、取原始输出** → 一律用 **`adb exec-out <cmd>`**（不做 PTY 转换，输出干净）。
- `adb shell` 适合**有明确输出边界**的短命令（`adb shell ls -l`、`dumpsys …`），但**一旦接管道做统计就必须换 `exec-out`**。
- 判据：**计数类结论若两次出现"文件数没变但内容变了"，先怀疑计数方式，而不是业务逻辑。**

### 定位器铁律

1. **必须从实测层级提取**，禁止凭命名习惯推测。踩过的坑：首页版本号是 `version_name`，设置页却是 `tv_version`，凭感觉写必错。
2. **五级自愈**：`resource-id → text → content-desc → class → 坐标兜底`；坐标兜底命中率要计数（>10% 说明定位体系退化）。
3. **id 可能被复用**：同一页面出现两个同样的 `resource-id`（分属不同列）时，`find()` 取首个会取错，需按 bounds 区分。
4. **可读文案与稳定 id 常常不在同一个节点上**：入口可点容器有 id 但 `text` 为**空串**，文案挂在其**无 resource-id 的子节点**上。此时按 `text="xxx"` 定不到、按容器 id 读 text 得空值 —— 正确做法是**「容器 id 定位 + bounds 包含关系取内部文案」**（筛出 bounds 落在容器内的非空文本，按 top 排序取最上方一条，避免误取角标）。实测：晨检仪顶部「错误提示」入口 `btn_face_error` 就是这样，最终才拿到 `'错误提示'`。
5. **未展开的浮层子项根本不在 dump 里**：下拉/浮层类控件收起时，其子项**完全不存在于 `uiautomator dump`**（实测：首页与台账页 dump 都查不到任一错误提示子项 id）。所以 ①「子项存在」类断言必须先执行展开动作；②展开类用例必须在 `finally` 里收起，并断言收起后读不到子项，否则污染后续用例的层级快照；③不得把「收起时读不到」误判成元素缺失缺陷。

### 两个必踩的时序坑

| 坑 | 现象 | 解法 |
|---|---|---|
| **跨页读取** | 先点进子页，再回头读首页元素 → 读到空值，误报「应用缺陷」 | 跳转**前**采集源页数据快照（`snapshot()`），挂到目标页对象上比对 |
| **异步渲染判定过早** | 元素已存在但 `text` 还是空，读到 `''` | 「页面加载完成」判定要包含异步元素，并轮询**文本非空**，不能只等元素出现 |

### 归因前置检查（省最多时间的一条）

用例失败后**先怀疑用例，再怀疑应用**，按序排查：

1. 定位器是否仍与实测层级一致？
2. 跨页数据是否在跳转前采集？
3. 上一轮的修复补丁**是否真的落进了文件**？（踩过：并发编辑导致修改丢失，却在按应用问题排查）
4. 设备在线/时间同步/权限变化？
5. 全部排除后才进入应用缺陷判定（C 候选 → 四步确认 → D 确认）

> 实测数据：31 条用例首轮 2 失败 + 6 错误，**100% 是用例自身缺陷**，无一例应用真缺陷。不做归因前置会白报 8 条假缺陷。

### 高价值用例类型：跨区域数据一致性

传统自动化只断言「元素在不在、文案对不对」。真正值钱的是**同一业务事实在多个位置必须自洽**，人工最容易漏：

- 统计卡：`已晨检 + 未晨检 == 总人数`
- 名单与计数：未晨检名单人数 == 未晨检统计数
- 列表与计数：台账列表条数 == 已晨检数
- 跨页：子页 Tab 计数 == 首页统计卡
- 跨端：设备显示值 == 后端存储值

一致性用例应占自动化用例的 **30% 以上**。

### 从设备日志还原业务数据源（判定「到底谁错了」的杀手锏）

一致性用例只能告诉你"两个地方对不上"，**说不清是谁错**。要定性，必须拿到**第三方数据源**。设备端 App 通常在关键路径把**接口原文 / 列表数据源**打进日志，抓它比要后端账号快得多：

```bash
adb shell "logcat -d -v time" > full.txt          # 一定要 -d 全量 dump，不要流式
grep -aoE "(OldList[12]|需要删除的[^:]*):\[.*"  full.txt   # 列表数据源
grep -aE "最新.*数量|refreshData|sign\(\)|发送数据：http"    full.txt   # 服务端返回值与请求 URL
```

实测晨检仪一次就拿到三层证据：

| 层 | 日志锚点 | 拿到什么 |
|---|---|---|
| 服务端 | `SplashActivity: 最新晨检记录数量：3` | 后端认为今天有 3 条 |
| App 数据源 | `MainActivity.refreshData(): OldList1:[...]` | 首页列表的**原始 JSON 数组**（可 `json.loads` 出条数与各字段） |
| App 另一数据源 | `OldList2:[...]` | 另一套口径（本例含"无体温"的下班项，5 条） |
| UI | 截图 / `uiautomator dump` | 卡片 3 张、统计卡「已晨检 2」 |

**三点实用经验**：
1. **括号配平后 `json.loads`**：日志里的 JSON 常被截断，不要用正则硬抠；写个小函数扫描 `[`/`]` 配平（注意字符串内的括号与转义）再解析，能直接得到结构化字段。
2. **时间戳要换算**：字段是 13 位毫秒 epoch（`1789535885000`），换算成 `YYYY-MM-DD HH:MM:SS` 才能与 UI 上看到的时间对齐 —— 这一步经常直接暴露"同一人两条记录相差 38 秒"这类关键事实。
3. **结论要克制**：本例拿到原文后，**推翻了自己先前提出的两个假设**（"渲染错位"、"本地缓存与服务端不同步"）—— 首页渲染与它自己的数据源**逐条一致**。真实问题只是**「按人计数」与「按条渲染」两套口径被并排展示**。**没有数据源原文时，不要写"疑似渲染错位"这类结论。**

> **反例警示**：同一份日志里 `OldList1`=3、`OldList2`=5。若不看字段直接比数字，会得出"数据源打架"的错误结论；实际 `OldList2` 混入了无体温的下班项，**不代表晨检记录有 5 条**。**比条数之前先比字段构成。**

### 安全与取证

- **只读优先**：涉及写入真实业务数据的流程（打卡、扣费、清零）默认**不纳入**日常回归；未授权时只验证「入口存在且可点击」，绝不触发真实提交。
- **取证要覆盖 fixture 阶段**：只在用例执行体挂截图钩子的话，页面加载超时（fixture 断言失败）将**完全没有证据**，无法举证。超时时必须主动截图 + 落盘层级。
- **日志扫描先过滤自噪声**：`uiautomator`、`AccessibilityNodeInfoDumper`、`Fetch time` 是自动化自己产生的，不滤掉会当成应用异常。

### ★ 证据归档与删除（先验证「可恢复」再动手，2026-09-24 踩坑）

**证据目录长得很快**：一次端到端采集的录屏 + 逐帧抽帧很容易到 **100MB+ 量级**（实测单项目 505MB：录屏 118MB、PNG 抽帧 112MB、JPG 抽帧 93MB、APK 177MB）。

**动手前三条**：

1. **查依赖，别删到断言资产**：自测/回放常依赖具体帧（如 `recon/e2e_seq/e2eseq/004~010.png`）→ 先 `grep` 工具代码里的路径引用，再决定哪些帧可动。**被依赖的帧不要转 JPG**（颜色签名会漂移，判据可能失准）。
2. **留替代证据再删大件**：删 mp4 前确认**逐帧抽帧 + logcat + 全帧扫描结果**已留存——结论的可复现性靠这些，不靠原视频。
3. **「走回收站」≠「可恢复」（强制验证）**：删后必须核查回收站内有**数据实体（`$R`）**，而非只有元数据（`$I`）。
   实测本机：`$I` **9094** 条 ／ `$R` 仅 **19** 条 → **回收站只留元数据、数据实为不可恢复**。
   > **声称「可恢复」前先验证**；否则按「不可恢复」表述并**事前**征得确认。要真可恢复 → **先手动复制备份，再删原件**。

**归档惯例（沿用既有结构）**：同级项目已有 `evidence_archived_r1`~`r5`（每轮一个目录 + **`MANIFEST.md`**，`NNN_SETUP_*.png` ／ `NNN_AFTER_*.png` 命名，单轮 13–24MB）→ **新轮次照建 `evidence_archived_rN/` + MANIFEST.md**，不要另造结构。

**归档操作三步法（2026-09-24 实测；工具 `tools/arch_evidence.py`）**：

1. **先扫依赖，再决定动不动**。用 `arch_evidence.py scan` 把工作目录按「硬依赖 ／ 被引用 ／ 未引用」分类。
   实测教训：某轮 `recon/` **458 个文件全部被引用，「未引用」= 0** —— 即**根本没有「纯冗余」可删**；想当然地删抽帧，会直接毁掉结论的原始证据（尤其当原视频已删时）。
2. **切分点：工作区 vs 引用**。同一目录在代码里有两种形态 ——
   `os.path.join(ROOT, "recon", ...)`（工具的**输出目录**＝工作区，**不许改**）与文档里的 `recon/xxx`（**引用**，要改）。
   → **用带斜杠的前缀 `recon/` 做全局替换**，可天然避开前者（`"recon"` 不带斜杠）→ 零误伤。
   > 写成 `os.path.join` 形式的**读取路径**（如 selftest 基线）无法自动区分读写，**必须逐个显式修正**。
3. **归档 = 移动 + 重建空工作区，不是删除**。语义分清：`recon/` = 采集工作区，`evidence_archived_rN/` = 定稿冻结。
   **完成后必跑 `selftest` / `replay` 回归**，验证工具没被改坏（这一步是归档的验收门槛）。

**批量文本替换必须二进制读写**：`open(p,'rb').read()` → `.replace()` → `open(p,'wb').write()`。
用文本模式（`open(p, encoding=...)`）会因 universal newlines **把 CRLF 悄悄改写成 LF**，导致整个文件在 diff 里「全变了」。

> **注意**：归档**不改变体积**（只是移动）。要真正减重，只有「APK 瘦身」或「清冗余抽帧」两条路 —— 而后者往往并不存在。

**工程提示**：

- 采集工具多自带清理开关（如 `e2e_assert.py record --drop-video` 断言后自动删中间 mp4）→ **优先用**，别事后手工清。
- 本机 **PowerShell 工具无 stdout 回显**（ConPTY）→ 需要输出时改走 Bash/Python；批量删文件用 Python `ctypes.SHFileOperationW`（规避中文路径在 shell 的编码问题）。

### 稳定性验证与 flaky 判定（别把「不通过」当「不稳定」）

连续 3 次不通过有**三种性质完全不同**的形态，混判会把最有价值的用例踢出门禁：

| 形态 | 特征 | 处置 |
|---|---|---|
| **flaky（真不稳定）** | 3 次结果**不一致**，时成时败 | 标记 flaky，限期修复，不得进门禁 |
| **确定性失败** | 3 次**一致失败**，已归因到被测对象缺陷、有可复现证据 | 标 `blocked(缺陷编号)`，**保留在门禁内**，缺陷关闭后自动恢复 |
| **数据／环境漂移** | 3 次结果不一致，差异可归因到**外部数据变化** | 标 `data-dependent`，补数据快照或桩后方可进门禁 |

> **判 flaky 的依据是「结果不稳定」，不是「结果不通过」。**
> **为什么这条要紧**：把确定性失败一律判 flaky 并踢出发布门禁，等价于**惩罚那些真正发现缺陷的用例** —— 门禁里只剩「永远通过」的用例，门禁从此失去意义。

**跑 3 次之前先确认三件事**：

1. **设备探活**：`ping <ip>` + `adb connect`。设备断电/移出网络是最常见的「验证做不了」原因，`adb kill-server && adb start-server` **救不了真离线**。
2. **数据快照**：依赖当日业务数据的用例（如「首页列表条数 == 已晨检数」），3 次执行前先比对关键计数/最新记录时间戳是否一致。**验证期间有人打卡 → 条数 3 变 4 → 用例由失败转「通过」—— 这种通过毫无稳定性含义。**
3. **时间窗收敛**：跨天或跨定时任务刷新周期的 3 次结果不可比。

**通过率口径**：`3 次全通过的用例数 ÷（总用例数 − blocked 项）`，blocked 项单列、不计入分母。

## 八、把实测结论回填到测试用例表（xlsx）

用户常在测试后要求「更新测试用例」。目标是**在保留原有用例的前提下，把本轮覆盖和缺陷沉淀进去**。

### 铁律

1. **先备份再动**：`cp 用例.xlsx 工作区/backup/用例.bak_YYYYMMDD.xlsx`，并检查同目录有无锁文件（`~$xxx.xlsx` 表示用户正打开着）。
2. **只增不改**：已有用例的编号/模块/测试点/预期结果**一律不动**，只填「实际结果 / 测试备注」两列。
3. **编号续接**：沿用原编号规则往后排（如原 `IO-1~49` → 新增 `IO-50~`），不要重编。
4. **格式对齐**：新增行必须复刻原有的合并单元格方式（模块/子模块/功能点按组纵向合并）、字号、对齐、边框、行高。

### 更新内容从哪来

| 来源 | 落成什么用例 |
|---|---|
| 本轮页面动线（`ui_*.log` 前台 Activity 变化） | 每个新覆盖的页面 → 加载 / 跳转 / 返回 用例 |
| 本轮成功打通的业务链路（接口 `"msg":"xxx成功"`） | 端到端链路用例 + 数据核对用例 |
| **每一条缺陷** | 一条**回归用例**，把缺陷现象写进「预期结果」，级别标在「测试备注」 |
| 上轮遗留 / 未复现项 | 标「部分通过（本轮未复现，需多轮确认）」，**不得写「已修复」** |
| 新解锁的可测性能力 | 把原本「靠人工目视」的项升级为「离线数据核验」用例 |
| 未触及的功能点 | 统一标 **`未覆盖`**，便于下轮筛选 |

> 状态用词要克制：`通过` / `不通过` / `部分通过` / `未覆盖`。**只有实测证据支持的才填结论，没测的一律 `未覆盖`**；「未复现」≠「已修复」。

### 核验

改完用 openpyxl 抽查：表头未变、行数 = 原条数 + 新增条数、抽 3 条原有用例确认内容未被动过、打印所有「实际结果」非空行校对结论。

> 表格内操作走 `tencent-docs-sheetagent` 委派（主代理不要直接用 openpyxl 做写入）。
