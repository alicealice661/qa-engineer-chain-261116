# 禅道 Bug 自动提单

## 链路位置（本包 qa-engineer-chain，先看这段再动手）

- **上一棒**：任意一段产出的缺陷清单 —— `android-adb-test-monitor` 的复测结论、`device-e2e-flow-driver` 的失败步骤、`network-only-device-recon` 的漏洞清单、`server-resource-trend-analyzer` 的导入 CSV。
- **本技能**：CSV / 自动化 JSON / pytest-junit → 禅道 Bug 单（填字段、切三段、挂截图、查重、回收单号）。
- **下一棒**：单号回到报告里；后续跟踪用 `zentao-cli` 查询与流转。
- **别用本技能做**：① 只是查单、改状态、看我的待办 → `zentao-cli`；② 还没定稿的缺陷清单 → 先出计划（本技能不带 `--confirmed` 只出计划，正好用来审）。
- **凭据红线**：`config.json` 是明文，不随包分发、不进 Git；密码不许回显、不许写进任何文档。
把**缺陷清单**变成禅道里的 Bug 单：填字段、切三段、挂截图、回收单号、查重、体检。

上游三种入口，用 `--from` 指定，按扩展名自动分派：
- `.csv` —— 人工整理的清单
- `.json` —— 自动化测试产出的结构化结果（**测试跑完直接提单用这个**，见 3.1）
- `.xml` —— pytest/junit 报告，失败用例自动转单（见 3.1）

实测环境：禅道**开源版 18.7**，PATH_INFO 伪静态，`http://192.168.2.121:8099`，产品 4 / 项目 210。
已实战提交并验收：#6655、#6656、#6657、#6658、#6659。

> **同事第一次用？** 直接照 **第零节** 走：逐项问答 → `init_config.py` 生成配置 → `--verify` 体检 → `--dry-run` → `--submit`。
> 技能安装：把整个 `zentao-bug-autosubmit\` 目录放进 `~/.workbuddy/skills/`，重启 WorkBuddy 后说「用禅道提单技能提 bug」即可。本技能不依赖任何 MCP / 外部服务。

## 一、字段口径（本现场定稿，换现场按需改）

**只填 7 项，其余 15 项一律留页面默认**：

| 页面字段 | 值 |
|---|---|
| 所属项目 | 210（二期） |
| 影响版本 | 主干 `trunk` |
| 当前指派 | 杨小伟 `yangxiaowei` |
| 反馈者 | 杨昌华 |
| Bug类型 | 代码错误 `codeerror` |
| Bug标题 | `<端前缀>——<设备名/系统名> <缺陷标题>`（**设备名必填，见 1.1**） |
| 重现步骤 | 步骤 / 结果 / 期望 三段 |

### 1.1 标题规范：端前缀 + 设备名/系统名 + 缺陷标题

**定稿格式**（2026-10-27 老大明确追加）：`——` 后面先写**设备名 / 系统名**，再写缺陷标题。

| 端 | 标题长这样 |
|---|---|
| PC端 | `测试PC端——智慧后勤系统 在线用户列表接口匿名可访问` |
| APK端 | `测试APK端——出入库秤 同步进度文案与进度矛盾` |
| APK端 | `测试APK端——体脂秤 完善基础信息年龄可输入 999` |
| IGW端 | `测试IGW端——智能网关 配置接口未鉴权` |
| 攻防 | `【高危】网络安全攻防——<系统名> xxx`（**仅在显式给了设备名时才加**，老单格式不变） |

设备名的两个来源，优先级从高到低：
1. 清单的 **`设备名`** 列（CSV 也认 `设备`/`终端名称`/`系统名`/`所属系统`；JSON 认 `device`/`设备名`/`system`）——**一份清单混多台设备时必须用这一列**
2. `config.json` 的 **`devices`** 按端兜底：`{"PC": "智慧后勤系统", "APK": "体脂秤", "IGW": ""}`
3. 都没有 → 该条不加设备名（保持老格式）

三个去重规则（实现见 `build_title()`）：
- 标题**已经带了端前缀** → 只补插缺失的设备名，不重复加前缀
- 标题**本身已以设备名开头**（如「体脂秤一键测量用例超时」）→ 不再重复拼设备名
- 设备名为空 → 退化成 `<前缀>——<标题>`

> 提问口径：接单前必问一句「这条是哪个设备/哪个系统？」——APK 端尤其要问（体脂秤 / 出入库秤 / 取盘机 / 留样柜 / 晨检仪），别一律写 APK。

留空：所属执行、截止日期、通知邮箱、操作系统、浏览器、相关需求、相关任务、抄送、联系人、关键词、附件（无图时）。
**不动**：所属产品（页面默认）、所属模块（`/`）、严重程度（3）、优先级（3）。

标题四档：`测试PC端` / `测试APK端` / `测试IGW端` / `【严重·高危·中危·低危】网络安全攻防`，分隔符是**全角双破折号 `——`**，其后紧跟**设备名/系统名 + 空格**，再写缺陷标题（见 1.1）。
等级换算：严重/致命→【严重】、高/高危→【高危】、中→【中危】、低→【低危】。

## 二、三段切分规则（改前先看这段，容易踩）

| 段 | 来源 | 规则 |
|---|---|---|
| **步骤** | 清单「重现步骤」 | 「预期结果/期望」之前的正文 |
| **结果** | 同上 | 只收**实测返回行**：行首 `→`，或 `→` 后紧跟 `HTTP/code=/状态码/2xx/4xx/5xx/{`。去序号、去重、最多 6 条、`；`连接。摘不出来就**不写该段**（不编造） |
| **期望** | 「解决方案建议」优先 | 没有才退回原文「预期结果：」后的内容 |

> ⚠ **必须排除菜单路径箭头**：`系统管理 → 用户管理` 会被误判成实测返回，把「结果」段污染成半句前置说明。已由 `RESULT_PAT` 处理，改动时别退回宽匹配。

写入编辑器的 HTML 用 `to_html()` 生成，两条硬约束：
1. **同组编号必须共用一个 `<ol>`** —— 空行只切 `</li>`、不关 `</ol>`。因为 **KindEditor 会剥掉 `ol[start]` 属性**，靠 start 续号必然失败，表现为「步骤序号全是 1.」。
2. 缩进续行用 `<br>` 并入上一条 `li`，不要另起 `<p>`，否则一步被拆成多段。

## 三、跑法

```bash
PY="${PYTHON:-python}"   # 用固定 venv 时改成 <venv>/Scripts/python.exe
S=scripts/zentao_ui_submit.py

$PY scripts/init_config.py             # 首次接入：交互问答生成 config.json（AI 代跑见 0.3）
$PY $S --verify                        # 配置体检：登录/产品/项目/指派人/清单/截图 六项（只读）
$PY $S --dry-run                       # 只看标题+三段切分，不开浏览器
$PY $S --dry-run --only ZH-SEC-05      # 单条看切分
$PY $S --dry-run --end PC              # 临时按 PC 端打前缀（不改 config）
$PY $S --submit                        # 全量提（默认带查重，命中即跳过）
$PY $S --submit --only A,B             # 指定编号（也认简写：--only 02,05 / SEC-04）
$PY $S --submit --force                # 关掉查重强提（慎用）
$PY $S --check 6655,6656               # API 体检 deleted/status
$PY $S --refresh 6656:ZH-SEC-05        # 用当前逻辑重刷已有单正文
$PY $S --refresh 6661:SAMPLE-01 --retitle   # 标题也按当前规范重写（标题规范变更后刷老单用）
$PY $S --attach 6656:ZH-SEC-05         # 按编号规则给已有单补附件
$PY $S --attach 6656:ZH-SEC-05 --attach-file a.png b.png
$PY $S --delete 6659                   # 删单（真删地址是 -yes-）
$PY $S --count                         # 由我创建的 Bug 状态分布
```

- 配置默认读脚本同目录 `config.json`；用 `--config` 或环境变量 `ZENTAO_CFG` 覆盖。
- 登录态缓存在 `state.json`，失效会自动重登。
- 每条结果写 `提报结果_<时间戳>.csv`：编号 / bugID / 状态 / 链接 / 附件 / 错误。

### 3.1 上游不止 CSV：自动化测试结果也能直接提

`--from` 按扩展名自动分派，三种入口最终都收敛成同一份 job 结构，后面切三段、抓图、提单完全一致：

| 扩展名 | 来源 | 适用 |
|---|---|---|
| `.csv` | 人工整理的清单 | 现在这套流程 |
| `.json` | **自动化测试产出的结构化结果**（推荐） | WorkBuddy/脚本跑完直接落 JSON |
| `.xml` | pytest / jest 的 junit 报告 | 已有 pytest 流水线，失败用例直接转单 |

**JSON 格式**（数组，也认 `{"findings":[...]}` / `{"bugs":[...]}` 包装）：

```json
[{"no": "AUTO-01",              // 可省，省了按 AUTO-001 编号
  "title": "人员变更记录导出接口未鉴权",   // 必填
  "severity": "高",              // 可省，省了按关键字启发式判级
  "end": "攻防",                 // 可省，省了用 config.end
  "steps": "1. 低权限账号登录\n2. 请求 /api/.../export\n→ code=200, total=21807",
  "solution": "补 @RequiresPermissions 注解",
  "evidence": ["C:/x/evidence/AUTO-01.png"]}]   // 可省，指到具体文件
```

中文字段名同样认：`编号 / 标题 / 严重程度 / 端类型 / 设备名 / 重现步骤 / 解决方案建议 / 截图`。
`steps` 里带 `→` 的行会自动进「结果」段。

**junit.xml**：只取 `<failure>` / `<error>` 的用例，通过的用例不进提单池。标题用「用例名 + 断言首行」，`AssertionError:` 之类前缀会被去掉。

**三道安全闸（自动化来源专有，别想着绕）：**

1. **默认不许提交**：`--from x.json --submit` 会直接 `[BLOCK]`，只打印计划。核对后加 `--confirmed` 才放行。
2. **判级是启发式的**：JSON 里没给 `severity` 时按关键字猜（泄露/越权/未授权→严重，500/异常→高，文案/样式→低，其余中）。**猜的级别必须人看一眼**。
3. **junit 判断不了端类型**：没给 `--end` 时会警告，否则整批按 `config.end` 打前缀（默认攻防，业务用例会被打错）。

```bash
$PY $S --from 结果.json --dry-run              # 先看：标题/三段/附件/端类型分布
$PY $S --from 结果.json --dry-run --end PC     # junit 场景指定端
$PY $S --from 结果.json --submit --confirmed   # 确认后真提（查重照常生效）
```

**为什么不让它全自动提**：自动化判级和标题都是启发式，直接灌库会产出大量「标题像 bug、实际是环境抖动/用例写错」的噪音单，研发要一条条关。用户自己的 **C 候选 / D 确认** 双轨制就是这道闸，脚本里的 `--confirmed` 是它的机器实现。

## 四、四大控件坑（照抄即可，别自己试）

| 控件 | 现象 | 解法 |
|---|---|---|
| **iframe** | 主文档 DOM 查不到任何表单字段 | 一切操作走 `page.frame(name="app-qa")`；**每次 `goto` 后必须重新取** |
| **chosen** | `select_option` 一律超时（元素不可见） | `$('#id').val(v).trigger('chosen:updated').trigger('liszt:updated').trigger('change')` |
| **影响版本 picker** | 点 `.chosen-container` 会误中「操作系统」；`#openedBuild` 的 options 恒为空 | 点 `#pk_openedBuild-search` 展开 → 点 `a.picker-option[data-value="trunk"]` |
| **KindEditor** | 只设 `#steps` 的 textarea 会被编辑器内容覆盖回占位 | `KindEditor.instances[0].html(html)`，同时写 textarea |

**保存三件事**（少一件就失败或误操作）：
1. 拦掉 `custom-ajaxSaveCustomFields`（响应体是 `parent.location.reload(true)`，会把填好的内容全冲掉）；
2. 点保存前先 `Escape` + 移除 `.picker-drop-menu`（否则按钮被判不可见）；
3. 保存按钮限定 `.form-actions` 内按文本「保存」精确匹配（宽选择器会点中编辑器工具栏的「保存模板」）。

**附件**：随表单 multipart 一次性提交，页面限制 **50M**；必须走页面 JS 保存流程，原生 `form.submit()` 能建单但丢附件。
**建单后跳的是 Bug 列表页**，不是详情页 → 从列表内嵌 `<script>data="[...]"</script>` JSON 按标题匹配回收单号。

## 五、提交后必做的体检（这一步不能省）

```bash
$PY $S --check <新单ID>
```

判定标准：`deleted=false`、`status=active`、`product`/`project` 与配置一致、`openedBy` 是当前账号。

**为什么要单独体检**：`bug-browse` 列表会**隐藏 `deleted=1` 的单**，而这类单**仍能直接打开详情页、仍可编辑**，肉眼看不出来。一旦被置删除：
- 列表查重**永远查不到它** → 重复提单；
- 用户在产品里**看不到它** → 以为没提上去。

实测事故：两条单在提交后被置 `deleted=true`，靠 `--check` 才发现（列表最新只到前两天、详情页却一切正常、附件也还在）。

## 六、查重口径

`--submit` 默认先拉「由我创建」的全量标题（`bug-browse-{product}-0-openedbyme-...`，100 条/页）再比对：
- 比对键：标题 `——` 后半段前 12 字，**子串匹配**（人工单常在中间插「智慧后勤」这类模块名）；
- 命中 → 状态记「跳过(已存在)」，不建单；
- 本批新建的单会即时加进比对池，批内不会自我重复。

实测命中关系：ZH-SEC-01→#6642、ZH-SEC-03→#6648、ZH-SEC-06→#6641（都是人工单）。

**注意**：列表拉不全时（见第六节 deleted 问题），查重会漏。**查重通过 ≠ 一定没有重复**，批量前最好人工扫一眼产品近期 Bug 标题。
